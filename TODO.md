- [x] `$origin` -- added 2026-08-16. The page's own origin, supplied rather than discovered: from the request while rendering (`middleware.originOf`), from `location.origin` in the browser. - [x] a usage site inside an `<:include>`d file is never expanded -- fixed 2026-08-17. - [x] `markout build <docroot> <outdir>` -- ahead-of-time delivery as static assets. Implemented 2026-08-17 in [src/server/build.ts](packages/cli/src/server/build.ts).
  - Why it outranked the language work: the CLI served and never wrote, so Node in the request path was the only way to deliver a page -- and the audience [POSITIONING.md](POSITIONING.md) names as the beachhead, server-rendered Rails / Django / Laravel / PHP shops, is precisely the one that cannot add a Node process in front of its app. Not a convenience: it is what makes the stated audience addressable at all.
  - Not client-side rendering: the same `renderPage` the middleware runs per request, run once per page at build time, so the markup is in the file and a page's static content does not flash in after the runtime loads. That is the property that distinguishes this mode from Alpine rather than merely matching it, and the CLI test asserts the resolved value is in the output.
  - `DEFAULT_RUNTIME_SRC` stopped being dot-prefixed, becoming `/markout-runtime.js` in BOTH modes -- the bundle's own filename on disk. The dot was sound while the middleware ANSWERED the path, since then it is never a file and cannot be shadowed by real content; it stops being sound the moment a build makes it a real file on somebody else's host, because a dot is what hosts use to decide a file is not for publishing (GitHub Pages runs Jekyll, which drops dotfiles without a `.nojekyll`; denying dot-paths is common hardening). Two names for one artifact was considered and dropped: one name, and the plain one, since the failure it risks (a docroot file shadowed while serving) is detectable and the one it avoids is a 404 on every page of a host you do not control.

  - A compile error exits non-zero with `file:line:column: message`, because this is the half of the checking a static host can never do later: a served page reports its errors to whoever asks for it, a built one is read by somebody who cannot see the console. A RENDER error does not fail the build, matching what the server does with the same failure.
  - `-p/--page` needed `enablePositionalOptions()`, not just a subcommand. Commander matches an option against the PROGRAM wherever it appears, so `build src out -p index` handed `-p` to `--port` and the build silently saw no page -- it compiled everything and copied every asset, which looks like success.
  - Symlinks are followed. `kits/bootstrap/std-kit` is a link to the kit next door, and a linked directory is neither a file nor a directory to `readdir`, so trusting the dirent copied a directory as a file (`ENOTSUP` on the first real docroot tried).
  - Assets: everything that is not `.html`, `.htm` or dot-prefixed is copied, which is what `express.static` already serves from the same directory. That means a docroot with source in it publishes it -- the site's own `server.ts` lands in the output (`orbit-db.ts` did too, until Orbit stopped having a back end). Faithful to the served mode and still a footgun, which is why the report prints the extensions it copied rather than only a count. Whether `build` should refuse or exclude known source kinds is undecided; a denylist invented here would be arbitrary.
  - Dot-prefixed names: skipped, except `.well-known/`, `.nojekyll` and `.htaccess`, which a deployable needs. An ALLOW-list because the two sets differ in kind -- what a host must serve is short and standardised (RFC 8615 for the first), while what must never be published grows with every tool installed and includes `.env`. `/.well-known/` is served too, which the blanket `/.` refusal had made impossible: a certificate could not be issued for a docroot markout was serving. It needed its own `express.static` mount, since declining the path is not enough -- static will not serve a dot-path on its own. `.nojekyll` and `.htaccess` are copied but NOT served: a host reads those, a client never asks for them.

Pre-existing; `build` used `path.resolve` from the start, which is how the two came to disagree.

- [x] a build that refuses what it cannot deliver -- done 2026-08-17. A `:server-` value that fails now FAILS `markout build`, and its page is not written.
  - The rule, and why it is that rule: whether the browser can repair the failure. An ordinary value that throws while rendering is re-derived there and may well succeed -- `${user.name}` asked before its datasource answered is the everyday case, and the served page is fine -- so a build warns. A `:server-` value crosses FROZEN, with a result and no expression, so nothing re-runs it: whatever it failed to produce, the page is without permanently. `RuntimeError.serverOnly` carries the distinction, set in `CoreContext.onError` from the value that failed, because phase cannot tell them apart -- a rejected promise (`settle`) and an expression that throws outright (`update`) are both this kind.
  - NOT the compile-time refusal of `:server-` values this entry used to plan, and the reason is worth keeping: a value that reads nothing of the request works perfectly well at build time, and baking its answer into the markup is what static site generation IS. Whether a given value needs a request is also decided at runtime -- `std-data` holds the same `:server-` value whether it is inert or a fetch, depending on `:client` -- so no static check could separate them. The render can, and the build runs one.
  - Two `std-data` fixes came with it, and the first was a real defect: `:_url` resolved `:url` against `$origin` unconditionally, so `new URL('/d.json', undefined)` threw when there was no origin. That value is computed whether or not the fetch happens, which meant `:client` -- the mode documented as the way to have data in a BUILT page -- was itself unbuildable. It now leaves a relative url alone, which is right anyway: the browser re-derives it against a real `location.origin`.
  - The second: a served datasource with a relative url now REJECTS with a message naming the fix, instead of the page rendering blank. Deliberately unlike a 404, which this component carries back as a value on the grounds that it is a fact about the page's data -- "there is no server here" is not that. It is the datasource being written for a delivery this page is not getting, which only the author can fix, so it is said where the author will see it. Building Orbit went from nine `Invalid URL` warnings and a silently dataless page to nine sentences and a non-zero exit.
  - Still open, and unchanged by this: whether one docroot can produce both, or whether a page declares which mode it is for. What is fixed is that a page which works in only one of them says so at build time rather than at a visitor's first paint.

- [ ] a build whose data was simply not there
  - Noticed 2026-08-17 while verifying the entry above, and left alone deliberately. `markout build` with an ABSOLUTE `:url` fetches while the page is built, which is the static-generation case worth having -- and if that fetch fails (the API down, a 500, DNS), `std-data` carries the failure back as its `error` value, nothing is reported as a render error, the build exits 0, and the page ships with the error in it instead of the data.
  - Which is the component's own rule, and the right one for a SERVED page: a 404 is a fact about the page's data rather than a fault in the render, so it reaches the page instead of a log the visitor cannot see. A served page is also rendered again on the next request, so the bad answer lasts seconds.
  - A built page is final, and that is the whole difference. An API that was down at 3am produces a deploy where every page says so, with a green build behind it -- the same "quietly wrong" shape the `serverOnly` rule just removed for a relative url, surviving in the absolute one.
  - The candidate fix, which would keep served behaviour identical: `std-data` rejects rather than carrying an `error` when the fetch fails AND there is no `$origin` -- the same signal the current fix reads, since no origin means no request means nothing will render this page again. It is a build failure exactly when the answer cannot be retried.
  - What makes this more than a `std-data` detail: "is this render final?" is not something a page can ask. `$origin`'s absence approximates it, and reading an approximation is how a component ends up encoding a delivery mode it was never told about. If pages are ever to adapt deliberately, that primitive is what the entry above is really asking for.

- [ ] markout services, and the SSR shortcut they would make sound
  - A datasource reaches its data by URL, so the same component works in the browser and while rendering. That is the point of `std-data` and it is what makes it convincing as an ordinary component -- but server-side it means the page fetches its own API over HTTP from inside the process serving it.
  - Measured on Orbit 2026-08-17, when it still had an API of its own (see the entry at the top of this file; the numbers stand as a measurement of the shape, not of any page in the repository today) (one shared db instance, the two modes alternated so warm-up favours neither): the render costs 70.6ms with its sources over loopback HTTP and 54.4ms with them answered in process, so the hop is 16.2ms of it. Only ~4ms of that is HTTP framing -- nine parallel loopback fetches cost 25.4ms against 21.2ms for the same nine db calls, and the db IS the 21ms. The rest is the settle waterfall: `incidents` cannot be asked for until `services` answers, so the render pays round-trip latency twice, through the whole Express stack each time.
  - Interception would work and needs no page changes. `renderPage` can inject a per-render `fetch` through `addedGlobals`, which override the built-ins in CoreGlobal -- scoped to one render rather than patching a global, which matters now that different pages render concurrently -- and the middleware can reach its own app through `req.app` and dispatch a synthetic request in process. Same-origin shortcuts, everything else falls through.
    - It would have to KEEP the JSON round trip. Skipping it looks like free savings and is not: the browser receives a `Date` as a string, so a shortcut that hands over live objects gives SSR richer types than the client, which is the exact divergence the HTTP design exists to prevent. It costs 0.3ms.
    - And it should be opt-in rather than automatic, because it reintroduces a server-only path for data loading. When it diverges -- middleware ordering, a header, a route that treats a synthetic request differently -- the bug appears only in SSR, which is the worst place to look for one. One flag to flip makes "is my datasource lying to me" a one-step answer.
  - The version worth building instead: a datasource declared as a markout SERVICE rather than as an arbitrary URL. Then markout owns both ends of the contract and the shortcut is sound by construction rather than by interception -- no synthesized requests, no hoping Express behaves the same both ways. It would also allow what interception cannot: knowing which services a page needs before the render starts, and so collapsing the waterfall that costs more here than the transport does.
  - Not urgent. 16ms on a page that renders in 70, against a change that touches how data reaches a page in one of the two environments it has to reach it in identically.

- [x] server-only values — `:server-name=${expr}` means "this expression runs on the server only; the client receives its result". Implemented 2026-08-16; design and decisions in [docs/design/value-transfer.md](docs/design/value-transfer.md), user-facing docs in [syntax.md](docs/reference/syntax.md#server-only-values).
  - Motivation is three classes of value hydration currently gets wrong: state assigned imperatively (a fetch payload exists nowhere in the served HTML, so SSR'd content is *wiped* on hydration), values derived from server-only inputs (file, env, DB, session), and non-deterministic ones (`Date.now()`, `Math.random()`) which don't break but visibly flip.
  - The value is **frozen** client-side — it arrives with `val` and no `exp`/`deps`, the inert shape `CoreGlobal` already uses. Freezing is correct for all three classes, not a compromise. The usage rule that follows: **keep the source, never the derivation** — mark `:server-user=${loadUser()}` and let `:greeting=${'Hi ' + user.name}` re-derive, or pinning the derivation silently decouples it.
  - **Two globals**: `__MARKOUT_PROPS` (app descriptor, function of the source, cacheable) and `__MARKOUT_STATE` (this render's state, per-request, never cacheable). Fusing them was considered and rejected: it costs a second full `escodegen` pass per request, mixes third-party bytes into the same script as all generated code, and closes the door on caching the expensive half. Nothing caches today, which is what makes the per-request half safe — and the split is the constraint any future page cache has to respect.
  - Format is a **JS object literal, not JSON**, so `undefined` (load-bearing: a failed expression yields `undefined` and never `null`), `Date`/`Map`/`Set`/`BigInt`/`NaN`/`-0` and cycles all survive with no tagged encoding. `JSON.parse('…')` parses ~2x faster and is the right trade only at hundreds of KB; deferred deliberately.
  - Escaping becomes security-relevant once a fetched payload lands in a `<script>`: `escapeScriptClose` handles `</script` but not `<!--`, and it was written for compiler-generated code, not hostile data.
  - Refusals landed in stage1 rather than stage2 as designed: stage1 is where the family prefix is determined, so the check costs one `if` next to the information instead of re-deriving it from compiled names.
  - Stencils are skipped when collecting, which the design missed: a `:for-each` host's values are prototypes for its replicas and are never evaluated, so collecting there sent `undefined` standing in for "never ran" — one spurious entry per list, and one per page for any `:for-data` not showing.
  - Name is still open — `:server-` describes the plumbing, not the contract. `:server-`/`:pin-`/`:once-` are closer. Now documented, but it is still one constant plus its refusal messages.

- [x] pending-work registry + async `renderPage` -- implemented 2026-08-16, and smaller than designed: there is no registry API. A `:server-` value whose expression returns a promise IS the registration, so a datasource is `:server-data=${fetch(src).then(r => r.json())}` with no new page-facing syntax. The rule that falls out: **async is allowed exactly where the result can be sent** -- an unmarked value's promise would have to resolve in the browser too, and hydration is synchronous. This also disposes of the `.json()` hole the design warned about, since what is awaited is the value's whole expression rather than `fetch`'s own promise.
  - **The runtime filters promises out of the reactive system.** A server value whose expression answers with a thenable holds it aside (`CoreValue.pending`) and reads as `undefined` until it lands. The first cut let the promise BE the value, and every problem after that came from there: a promise is truthy so guards passed and built requests out of `[object Promise]`, it has no `.length` so dependents threw, and rendering one printed `[object Promise]`. Pages are written against data; `undefined` is what "not there yet" already means everywhere else here.
  - Ordering survives as a smaller rule -- a value is not settled while one of its own sources is pending -- which still matters for an unguarded chain (`${Promise.resolve(a * 10)}` computes `NaN` before `a` lands). Guarded chains no longer need it.
  - Orbit (`kits/bootstrap/orbit.html`) is the end-to-end demo: ten `std-data` elements call its own API while the page renders, and the served console is complete. Nothing else in that page changed when its data stopped being a literal -- same filters, same charts, same tables over the same arrays. It brings its own express app (`kits/bootstrap/server.ts`), which is the truer picture anyway: an application has routes, and markout is the middleware that renders its pages.
  - Orbit is four files (`orbit.html`, `orbit/components.htm`, `orbit/sources.htm`, `server.ts`), split to show the shape an application takes. Components are imported, sources included -- a definition wants to arrive once per page however often it is named, an instance wants splicing exactly where it is written, since that is where its name resolves. `sources.htm` carries `:apiBase` on its root to show the token pattern is not a kit privilege.
  - One request per SET OF INPUTS. A value with sources re-evaluates whenever it is read in a new cycle, and settling anything opens one, so a server value whose request was in the air got asked again and again for the same thing -- ten sources, twenty-one requests. First fix was "don't re-evaluate while pending", which was too blunt: it also blocked the re-evaluation an unguarded chain depends on (`${Promise.resolve(a * 10)}` stayed NaN), and that silently made the settle loop's ordering rule inert. `CoreValue` now snapshots its sources' values when it starts a request and re-runs only if one of them moved. Kept for server values only, so ordinary values carry none of it.
  - NOTE the server-globals feature (`markout({ globals })`) is no longer exercised by any page now that Orbit goes through HTTP. It stays fully tested in `test/server/server-globals.test.ts`, but there is no demo of it -- worth one if a page ever wants in-process services rather than an API.
  - `renderPage` discards the whole first reading and takes it again once results are in, keeping only `settle` failures. A dependent still evaluates once before its sources arrive, and `${rows.length}` on `undefined` throws just as surely -- that is a value asked too early, not a broken page. Without this, dev mode replaced the page with an error about a value that was fine a millisecond later, which is how it was found.
  - Two limits, because they catch different things: a 5s deadline budgeted across the whole render (a slow network), and a 5-round depth cap (a page whose values feed each other too deeply, which would otherwise stall to the deadline on every request while reporting nothing but slowness). Either way the value becomes `undefined`, is reported under a new `settle` phase, and the page is still served.

- [x] `:if` -- added 2026-08-16. Truthiness, no item binding. The kit and Orbit's 28 conditions are now `:if=${cond}`, having passed through `:for-each=${cond ? [1] : []}` and `:for-data=${cond || null}` on the way.
  - The name was free because the language already refused it: a value has to be something an expression can say, and `${if}` does not parse. So a reserved word is a namespace no page can occupy, and a directive can take one with no prefix and no possibility of collision. The rule a reader ends up with is "if you could have declared it, it is a value".
  - Not every word that looks reserved is: acorn takes `let static async await yield of get set from as` as identifiers in sloppy mode, so those are NOT safe to claim -- a page can declare them today. The safe set is `if else for while do switch case default break continue return function class extends super this new delete typeof instanceof in void var const try catch finally throw with debugger import export null true false`.

- [x] `:aka` and `:slot` are literal-only -- 2026-08-16. They are the two system attributes spelled as ordinary identifiers rather than reserved words, kept that way deliberately: no reserved word reads as well (`:this` for `:aka` is close; nothing covers `:slot`, since `:in` is the only reserved preposition left and it is vaguer). The price of that choice is that a page cannot declare values of those names, and the point of the error is to make the price visible -- `:slot=${x}` used to stringify the expression, address `[object Object]`, match no slot and drop the content in silence.

- [x] `:else-if`/`:else` -- added 2026-08-19. Both compile to the same `if$` value `:if` does, since all three answer one question at one arity; what they add is a link to the branch before them, and the rule that the first condition to hold takes the position. `:else` is free for the reason `:if` was (a reserved word no page can declare), `:else-if` for a different one (a dash, which a plain value name cannot contain, and no `else-` family to claim it).
  - Sibling adjacency was the objection, and it turned out to cost one variable in the loader's child walk -- the question is only unanswerable AFTER loading, once every branch has been wrapped in a `<template>` and no element is next to what it was written next to. The rule is stated in the errors rather than left implicit: an `:else` needs a branch on the element immediately before it, and whitespace and comments are the only things allowed in between (anything that renders would appear between two alternatives at most one of which is showing).
  - Chosen over a value-graph chain, which would have needed dependency edges between sibling scopes -- machinery the compiler has none of, since `via` navigates only to `$parent` and named scopes. The runtime instead re-decides the whole chain from whichever branch's condition moved, which is what the graph could not do anyway: the branch that has to give up its position is exactly the one that did not change, so nothing would ever wake it.
  - Links are compiled as sibling ids (`elseOf`/`elseNext`), not references, which is what makes a chain inside a `:for-each` work -- a replica shares its host's child props verbatim, so every replica's branches carry the same ids and each finds its neighbour in its own copy. A lone `:if` carries neither prop, and takes exactly the path it took before.

- [ ] routing, in three layers with three different homes. Decided 2026-08-24; none of it is built. Nothing anywhere -- docs, POSITIONING, the site -- answers "what happens when my app has more than one page", and the multi-page answer is defensible with numbers behind it (an ordinary page compiles in ~2ms, the heaviest page here in ~111ms, and the middleware caches the compiler's output so a page compiles once per edit rather than once per request) -- but an unstated position reads as an oversight rather than a decision to anyone arriving from an SPA framework. What answers it is a component, because a component answers by existing.

  1. **Reading the page's own URL: the language.** `$origin` is the origin and nothing else, and the globals list refuses `location` because a browser-only name makes an expression that works in one half of an isomorphic render and throws in the other. But the path and the query are not headers or cookies: the server has them from the request, the browser has them from `location`, and they mean the same thing on both sides -- exactly the bar `$origin` clears. No router of any design can be written without this, it carries no opinion, and it is not kit material. Needs designing and naming (`$url`? a path and a search?) before anything else here can start. The middleware already holds the value: `renderPage` is handed `origin` and nothing else.

  2. **The address bar as read/write state: `std-kit`.** Reading is a global; NAVIGATING is a side effect with a lifetime -- a `popstate` listener to attach and detach, and state to hold. That is exactly the criterion std-kit's own README sets for what belongs in it: "`<stdio.h>` is the half that genuinely needs a scope, a lifetime and somewhere to keep state." One sensible design, which is what makes it safe to be ambient.

  3. **The router: a kit of its own.** Settled, and the reason is opinion rather than cost. `std-data` is "fetch a url, hand back what came back" and is barely a design decision; a router is a design SPACE -- exact versus pattern, nested versus flat, guards, hash versus history, scroll restoration, lazy loading. std-kit is spliced into every page by core and peer-depends on it, so its surface is effectively part of the language's: shipping one routing opinion there would make it THE opinion, in a project positioned as not an application framework, and a wrong ambient component is a migration where a wrong package is a version bump. `bootstrap-kit` is separate for precisely this reason, and routing sits beside it on that axis rather than beside `std-data`.
    - The cost argument was considered and does NOT support this, which is worth recording so nobody re-derives it: an ambient part costs ~1ms per page per COMPILE (measured: 0.8ms -> 1.8ms on a trivial page with std-kit spliced), and the middleware caches compiled pages, so that is once per edit in dev and once per process in production. Noise. The decision rests on where opinions may live, not on what they cost.

  - **Two different things wear the word, and only one is in scope above.** *In-page* routing is "which region of THIS page is showing, decided by the URL" -- `:if` over a value plus history, and layers 1 and 2 are most of it. *Between-page* routing is replacing the document without a round trip, which is the SPA question: a compiled page is one document, and swapping one for another is a mechanism markout does not have and may well not want. Worth deciding the second explicitly, because building the first will make people ask.

  - Layers 1 and 2 are worth building even if the router never is. They are what would let the desk demo's `?q=` survive a reload, which is a real gap today and needs no routing opinion at all.

  - No prior art here to copy: the desk demo looks like some and is not. Its `?q=` builds the DATASOURCE's url out of a page value; `location` and `history` appear nowhere in it. Its comments say so now, in all three places that used to say "the URL".

- [ ] `:switch`/`:case`/`:default`, postponed. All three names are reserved, so they are available on the same argument as `:if`. - [x] `class+=` / `class-=` / `style+=` / `style-=` -- 2026-08-24. A plain attribute replaces; its `+=`/`-=` forms contribute, and only `class` and `style` have them because they are the two attributes HTML gives a set rather than a value. That is the same fact that gives them a `:class-`/`:style-` family and gives `href` none, so the four are those families' whole-set forms: `class+=` of a truthy toggle, `class-=` of a falsy one.
  - Not `:` attributes, which is the part worth keeping. `:` names what HTML has no name for, and `class` has a name -- what is new is the OPERATION, and an operation is not a name. It also costs no reserved word: a `:class`/`:style` pair would have taken `style` out of the value namespace, and `class+=` takes nothing. The parser needed one character (`+` in `skipName`; `-` was already a name character, so `class-=` parsed before any of this) and the VS Code grammar one `L:` rule, because HTML's own reads `class+=` as `class` plus a stray `+` -- not illegal, just coloured as two things.
  - A literal is read the way HTML spells that attribute and an expression carries the typed value: `string[]` for three of them, `{ property: value }` for `style+=`, since addition assigns and removal only names. Folded in stage7, so nothing downstream ever meets the string form. The compiler names the two shapes reached for by accident -- an interpolation and a string expression -- and the runtime reports the rest, because `[...'mb-0']` is five classes.
  - **Nothing writes the attribute whole any more**, which is the half that was a bug fix. Each input records what it contributes, the four together say what the set should be, and only the difference is applied. A reactive `class=${...}` re-running used to turn `box box-red mine` into `box box-green` -- silently, and only once the variant happened to change -- and it did the same to a class Bootstrap's own JS had put on a modal it was handed. The base is stated in the props rather than read off the element, because after a round trip the element carries the SERVED result and taking that for the base means a contribution can never be taken back off.
  - `::extra` is gone from all 28 kit parts, which is what it was for: a convention every component author had to remember, hand-rolled into each class list. `::bodyExtra` on `bs-card` stays and says why the rest went -- `class+=` reaches a component's own element, and the card's body is a different one. The built site is unchanged class-for-class: every difference is order within the same set, or an empty token that used to come from `${extra ?? ''}`.
  - Two pre-existing bugs came out of it. `ServerStyleProp.cssText` split on `;` and `:` and so silently dropped `background: url(data:image/svg+xml;base64,...)` -- plain HTML, no markout syntax anywhere near it, and where the style is reactive the browser's own CSSOM disagreed with the server. And `ServerClassProp.fromString('')` left an empty-string member, which serialized as a leading space and, once classes were composed rather than assigned, survived every later add.
  - The warning came next, and settling one thing was the price of saying it. A usage site's `class="mine"` used to lose to a definition's reactive `class=${...}` and beat a static one -- one rule, two behaviours, decided by something the caller cannot see -- because a computed class is a value and values land after an instance's static attributes. The definition's value is dropped for that instance instead, so "a plain attribute at a usage site replaces the definition's" holds either way, and `<bs-alert> sets "class" itself, and a "class" here replaces it -- did you mean "class+="?` is true wherever it appears. A warning, on the same footing as `nothing reads "varient"`.
  - And a third pre-existing bug, found because `style+=` needs a base to argue with: `expandDefine` copied `className` onto the base element and not `style`, both being element properties rather than attribute nodes. So a static `style` on a `<:define>` reached nothing -- including `bs-toast-container`'s `style="z-index: 1090"`, which is what holds a toast above a modal's backdrop. Reading both through `getAttribute` also stopped every definition without a class from serializing an empty `class=""` into its stencil.
