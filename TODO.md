
- [x] `$origin` -- added 2026-08-16. The page's own origin, supplied rather than discovered: from the request while rendering (`middleware.originOf`), from `location.origin` in the browser. It exists because a `:server-` fetch of `/data.json` is not asking for a different address, it is not asking for an address at all -- the server has no page to be relative to. `std-data` resolves `:url` against it, so pages never write it themselves and a page-relative URL means the same thing in both modes.
  - Nothing else about the request is offered, deliberately: headers, cookies and method have no browser counterpart, so a page reading one would render something it cannot hydrate to -- and would publish a session while doing it. `$request` was considered and rejected on exactly that: the subset with the same semantics on both sides IS the URL.
  - Still open, and the natural next step if a router ever wants one: `$url` or `$location` for the full current URL, so `pathname` and the query are reachable. `$origin` is a strict subset, so nothing is foreclosed. The question it raises that `$origin` doesn't: a URL changes under client-side navigation, so a static snapshot goes stale, and whether it should be reactive is a real decision rather than an implementation detail.
  - `URL` joined the globals list alongside it, on the same footing as `fetch`: it exists in both environments, and resolving a relative URL against a base is what the kit actually needed.

- [x] a usage-site value naming its own parameter -- fixed 2026-08-16. `<x-tag :items=${items} />` where the definition declares `:items` read the parameter rather than the page value, compiled clean, and failed at runtime as `link: unresolved dependency` with the component blank.
  - Two rules disagreed about where such a value resolves. stage3 saw a value reading its own name and applied the shadow-skip meant for `<div :n=${n + 1}>`; stage4 resolved against the scope the usage ELEMENT was loaded into, which holds the value, so the name shadowed itself there too. Both hops landed one scope past the call site, which is where the runtime actually evaluates it (`CoreScope.hostFor`).
  - The exception both fixes keep: a usage carrying `:for-each` binds its per-item alias on itself, so `<my-tag :for-each=${rows} :x=${data} />` still resolves `data` there -- the runtime wraps that call site in a LoopSiteScope for exactly this reason. Caught by test/matrix.test.ts, which failed 8 ways when the first fix was blanket.

- [ ] `<:define>`s extending other `<:define>`s
  - `tag="my-card:my-box"` where `my-box` is itself a definition. Refused with a compile error 2026-08-16 rather than left as it was: `expandDefine` leaves the base tag as an ELEMENT inside the new stencil, so `<my-box>` in there is an ordinary usage site -- `expandCustomTagUsages` found it, expanded it, and replaced the very element `page.customTags` had just registered `my-card` against. Pages compiled clean, rendered clean, and showed nothing where the usages were.
  - Wanted because the kit's own vocabulary is otherwise a dead end for an app author: you can compose inside a component but not specialize one. In Orbit it is the navbar and the three overlays -- `bs-navbar`, `bs-offcanvas`, `bs-modal` -- that cannot become app components. The wrapper-`<div>` workaround covers the overlays (they are `position: fixed`) and fails for the navbar, since a `sticky` child cannot escape its parent's box.
  - The tractable semantics is delegation at expansion time, not scope inheritance: `<my-card :x=${1}>body</my-card>` expands to `<my-box :x=${1}>` carrying my-card's body plus the usage's content. A prototype chain through `CoreScope` would reach stage3/stage4 resolution and the runtime, and buys only the ability for a derived value to read the base's.
  - What it needs: definitions expanded base-before-derived (a topological sort over `customTags`, plus a cycle error); `className` concatenated rather than assigned (`expandDefine` assigns, which is what silently dropped the base's classes); three-level value precedence -- base defaults, derived, usage site -- where the derived's expressions resolve against the DERIVED definition, neither the base nor the call site, which lands on the same `callSiteValues`/`detachedUsageSite` machinery as the entry above; a rule for whether a usage's content reaches the base's `<:slot>` when the derived declares none; and an error for `:aka` colliding between base and derived.
  - Items 3 and 4 there are the feature. They are precedence and slot-routing rules, which is where a language accumulates surprises it cannot later change, so they are worth deciding deliberately rather than under a deadline.

- [ ] shrink the app props
  - Measured on Orbit 2026-08-17, compiled (not dev): props are 311KB raw / 25KB gzipped, against 157KB / 19KB of markup and a 21KB / 7.2KB runtime -- 65% of everything the page ships that is not the runtime, for 838 scopes and 1591 values (~195 bytes raw per value, ~16 gzipped). A whole page is 55KB gzipped including framework, logic, markup and data; a hello-world is 7.5KB. Neither number is a problem. The raw one is the one to work on, because gzip already collapses the repetition and the browser still parses all 311KB.
  - So this is a PARSE-and-allocate item, not a transfer item, and the two biggest costs are both shapes rather than content:
    - dependency thunks: 2051 of them, 83KB, **26.8% of the props**, each `function(){return this.$value('_sum');}` to say what `'_sum'` says. Emitting deps as data -- a key, or a via-path and a key -- would take that to roughly a quarter of the size and allocate 2051 fewer closures at startup. The runtime already knows how to walk a `via`/`key` pair; `ValueDepRef` IS that pair, and stage7 turns it back into a function.
    - `function(){return …;}` wrappers: ~27% of the props, and NOT replaceable by arrows as things stand, because the runtime evaluates with `exp.apply(scope.proxy)` and an arrow would capture the wrong `this`. Passing the scope as an ARGUMENT instead (`exp: s => s.x + 1`) buys both the wrapper and the shortening of 4988 `this.` to `s.`.
  - Lower value, only worth doing alongside: one-letter keys for `exp`/`deps`/`values`/`children` (~26KB raw, but gzip eats nearly all of it).
  - Not a redesign in either case, which is the point: the shape is compiled, so this is stage7 and the runtime's props contract agreeing on a cheaper encoding, with no page changing.
  - Related, and already done: `--prod` on the demo server (2026-08-17). Dev props are 5.4x compiled ones, so the page anyone reaches for to measure markout used to answer with 83KB gzipped instead of 49KB.

- [x] a usage site inside an `<:include>`d file is never expanded -- fixed 2026-08-17. The preprocessor spliced included nodes into the page by setting `parentElement` and pushing them onto the new parent's `childNodes` by hand, never touching `parentNode` -- which is the pointer `insertBefore`/`removeChild` actually read. So every included node was listed by the page while still claiming the fragment it came from as its parent, and anything that later tried to REPLACE one worked on a document nobody serves.
  - Custom-tag usages were the visible casualty: stage1 removed the tag from the fragment and left the copy in the page, which rendered as an unknown element with a scope and no instance behind it. Orbit's ten `<std-data>` elements were exactly this, and had been since the sources moved into their own file.
  - Reported nothing, at any stage, which is what made it worth chasing over a payload saving of 500 bytes: an include is a splice, and a splice that changes how the markup inside it compiles is the opposite of unobtrusive. `<:group>` flattening and literal includes had the same defect and were fixed with it.

- [x] server-only values — `:server-name=${expr}` means "this expression runs on the server only; the client receives its result". Implemented 2026-08-16; design and decisions in [docs/design/value-transfer.md](docs/design/value-transfer.md), user-facing docs in [syntax.md](docs/reference/syntax.md#server-only-values).
  - Motivation is three classes of value hydration currently gets wrong: state assigned imperatively (a fetch payload exists nowhere in the served HTML, so SSR'd content is *wiped* on hydration), values derived from server-only inputs (file, env, DB, session), and non-deterministic ones (`Date.now()`, `Math.random()`) which don't break but visibly flip.
  - The value is **frozen** client-side — it arrives with `val` and no `exp`/`deps`, the inert shape `CoreGlobal` already uses. Freezing is correct for all three classes, not a compromise. The usage rule that follows: **keep the source, never the derivation** — mark `:server-user=${loadUser()}` and let `:greeting=${'Hi ' + user.name}` re-derive, or pinning the derivation silently decouples it.
  - **Two globals**: `__MARKOUT_PROPS` (app descriptor, function of the source, cacheable) and `__MARKOUT_STATE` (this render's state, per-request, never cacheable). Fusing them was considered and rejected: it costs a second full `escodegen` pass per request, mixes third-party bytes into the same script as all generated code, and closes the door on caching the expensive half. Nothing caches today, which is what makes the per-request half safe — and the split is the constraint any future page cache has to respect.
  - Format is a **JS object literal, not JSON**, so `undefined` (load-bearing: a failed expression yields `undefined` and never `null`), `Date`/`Map`/`Set`/`BigInt`/`NaN`/`-0` and cycles all survive with no tagged encoding. `JSON.parse('…')` parses ~2x faster and is the right trade only at hundreds of KB; deferred deliberately.
  - Escaping becomes security-relevant once a fetched payload lands in a `<script>`: `escapeScriptClose` handles `</script` but not `<!--`, and it was written for compiler-generated code, not hostile data.
  - Refusals landed in stage1 rather than stage2 as designed: stage1 is where the family prefix is determined, so the check costs one `if` next to the information instead of re-deriving it from compiled names.
  - Stencils are skipped when collecting, which the design missed: a `:for-each` host's values are prototypes for its replicas and are never evaluated, so collecting there sent `undefined` standing in for "never ran" — one spurious entry per list, and one per page for any `:for-data` not showing.
  - Name is still open — `:server-` describes the plumbing, not the contract. `:server-`/`:pin-`/`:once-` are closer. Now documented, but it is still one constant plus its refusal messages.

- [x] pending-work registry + async `renderPage` -- implemented 2026-08-16, and smaller than designed: there is no registry API. A `:server-` value whose expression returns a promise IS the registration, so a datasource is `:server-data=${fetch(src).then(r => r.json())}` with no new page-facing syntax. The rule that falls out: **async is allowed exactly where the result can be sent** -- an unmarked value's promise would have to resolve in the browser too, and hydration is synchronous. This also disposes of the `.json()` hole the design warned about, since what is awaited is the value's whole expression rather than `fetch`'s own promise.
  - **The runtime filters promises out of the reactive system.** A server value whose expression answers with a thenable holds it aside (`CoreValue.pending`) and reads as `undefined` until it lands. The first cut let the promise BE the value, and every problem after that came from there: a promise is truthy so guards passed and built requests out of `[object Promise]`, it has no `.length` so dependents threw, and rendering one printed `[object Promise]`. Pages are written against data; `undefined` is what "not there yet" already means everywhere else here.
  - Ordering survives as a smaller rule -- a value is not settled while one of its own sources is pending -- which still matters for an unguarded chain (`${Promise.resolve(a * 10)}` computes `NaN` before `a` lands). Guarded chains no longer need it.
  - Orbit (`kits/bootstrap/orbit.html`) is the end-to-end demo: ten `std-data` elements call its own API while the page renders, and the served console is complete. Nothing else in that page changed when its data stopped being a literal -- same filters, same charts, same tables over the same arrays. It brings its own express app (`kits/bootstrap/server.ts`), which is the truer picture anyway: an application has routes, and markout is the middleware that renders its pages.
  - Orbit is four files (`orbit.html`, `orbit/components.htm`, `orbit/sources.htm`, `server.ts`), split to show the shape an application takes. Components are imported, sources included -- a definition wants to arrive once per page however often it is named, an instance wants splicing exactly where it is written, since that is where its name resolves. `sources.htm` carries `:apiBase` on its root to show the token pattern is not a kit privilege.
  - One request per SET OF INPUTS. A value with sources re-evaluates whenever it is read in a new cycle, and settling anything opens one, so a server value whose request was in the air got asked again and again for the same thing -- ten sources, twenty-one requests. First fix was "don't re-evaluate while pending", which was too blunt: it also blocked the re-evaluation an unguarded chain depends on (`${Promise.resolve(a * 10)}` stayed NaN), and that silently made the settle loop's ordering rule inert. `CoreValue` now snapshots its sources' values when it starts a request and re-runs only if one of them moved. Kept for server values only, so ordinary values carry none of it.
  - NOTE the server-globals feature (`markout({ globals })`) is no longer exercised by any page now that Orbit goes through HTTP. It stays fully tested in `test/server/server-globals.test.ts`, but there is no demo of it -- worth one if a page ever wants in-process services rather than an API.
  - `renderPage` discards the whole first reading and takes it again once results are in, keeping only `settle` failures. A dependent still evaluates once before its sources arrive, and `${rows.length}` on `undefined` throws just as surely -- that is a value asked too early, not a broken page. Without this, dev mode replaced the page with an error about a value that was fine a millisecond later, which is how it was found.
  - Two limits, because they catch different things: a 5s deadline budgeted across the whole render (a slow network), and a 5-round depth cap (a page whose values feed each other too deeply, which would otherwise stall to the deadline on every request while reporting nothing but slowness). Either way the value becomes `undefined`, is reported under a new `settle` phase, and the page is still served.

- [x] `:if` -- added 2026-08-16. Truthiness, no item binding, no `:else`. The kit and Orbit's 28 conditions are now `:if=${cond}`, having passed through `:for-each=${cond ? [1] : []}` and `:for-data=${cond || null}` on the way.
  - The name was free because the language already refused it: a value has to be something an expression can say, and `${if}` does not parse. So a reserved word is a namespace no page can occupy, and a directive can take one with no prefix and no possibility of collision. The rule a reader ends up with is "if you could have declared it, it is a value".
  - Not every word that looks reserved is: acorn takes `let static async await yield of get set from as` as identifiers in sloppy mode, so those are NOT safe to claim -- a page can declare them today. The safe set is `if else for while do switch case default break continue return function class extends super this new delete typeof instanceof in void var const try catch finally throw with debugger import export null true false`.

- [x] `:aka` and `:slot` are literal-only -- 2026-08-16. They are the two system attributes spelled as ordinary identifiers rather than reserved words, kept that way deliberately: no reserved word reads as well (`:this` for `:aka` is close; nothing covers `:slot`, since `:in` is the only reserved preposition left and it is vaguer). The price of that choice is that a page cannot declare values of those names, and the point of the error is to make the price visible -- `:slot=${x}` used to stringify the expression, address `[object Object]`, match no slot and drop the content in silence.

- [ ] `:switch`/`:case`/`:default`, postponed. All three names are reserved, so they are available on the same argument as `:if`. It beats `:else` structurally: `:else` needs sibling adjacency (which element, across what whitespace), while cases are CHILDREN of the switch, which the compiler already models. Decisions if it happens: strict equality like JS, first match wins with no fallthrough, `:case` must be a direct child, guards come free via `:switch=${true}`, and a non-matching branch evaluates nothing. Cost: it needs a container element, which `:if` does not.

- [ ] perhaps: component extension — `<:define tag="bs-fancy-input:bs-input">`, i.e. basing a definition on another component instead of a plain HTML tag. Motivation: a kit could offer a plain component and an enriched one without the two drifting, since the enriched one would be built from the plain one rather than copying its markup.
  - Currently accepted with no error and then broken. `expandDefine` builds the body as a literal `<bs-input>` element inside the definition's `<template>`; `expandCustomTagUsages` later walks into template content and expands it, consuming the extension's own `<:slot />` as content bound for the base's slot. With caller content you get `<x> was given content but its <:define> has no <:slot> to put it in` even when it has one; without caller content it renders NOTHING, silently. Worth at least rejecting a custom tag as a base until this is designed.

(2) Parameter merge: is `:label` on `<:define tag="b:a" :label=${''}>` declaring b's parameter or passing one to a? "Both — b's scope is a's scope with additions" is the answer that falls out of existing lexical scoping, but it needs stating.

The base has to expose the hooks (take `:invalid`, apply the class itself), at which point the extension only supplies policy — and that composition works today without any compiler change.

- [x] comptime constants -- implemented 2026-08-16. `:k_name=${expr}` is computed by stage5 and substituted into every reader; nothing of it reaches the runtime. The closure rule ("a `k_` value may read only literals and other `k_` values") is enforced, unsolvable is a compile error rather than a silent fall back to reactive, and the result must be a primitive since substituting an object would give every reader a separate copy. `:server-k_x` is refused: there is nothing left to send.
  - Measured on the Bootstrap kit's own tokens, which is the real theming path: ~1.2KB off Orbit. The 13x in the original note was a page that was mostly tokens; on a real page this is a cost-model fix rather than a payload one, and the compact-codegen change was the payload.

- [x] treeshake removes unused `<:define>`s -- 2026-08-16. A tag is used if stage1 expanded a usage site for it anywhere, including inside another definition's body; anything else loses its `<template>` stencil. Orbit drops 9 of 48 for ~3KB raw, 0.5KB gzipped.
  - Only markup: a definition's SCOPE was never in the props, since stage7 already filters definitions out of their parent's children. So the ceiling is what the unused components' markup weighs, which is why this is not a payload feature -- see the compact-codegen commit, which was 80%.
  - Deliberately conservative: a component reachable only through a definition that is itself unused survives. Removing it needs the usage graph rather than a flat set, and getting that wrong deletes markup a page needs.
  - Its real value is the item below: it is a prerequisite for eliding the runtime when nothing reactive survives.
  - `:when-used="tag-a tag-b"` (2026-08-16) lets an asset go with the components it belongs to -- a `<style>`, a `<link>`, a `<script>`. Opt-in rather than inferred from the fragment, because a stylesheet next to some definitions is not necessarily THEIR stylesheet: Orbit's is the page's, so "these definitions died, so these styles are dead" would be wrong rather than merely surprising. A tag no `<:define>` declares is a compile error, so a rename cannot silently leave a stylesheet waiting on a name nothing uses.
  - Nothing of it reaches the runtime, including the scope: an element is scope-worthy if it carries any `:` attribute, and a `<style :when-used=...>` given one took its own text with it -- the stylesheet rendered empty and its binding had nothing to write to. `:slot` was already excepted for the same reason.
  - Speculative until a kit ships per-component styles, and the Bootstrap kit never will: it wraps a monolithic framework, so the CSS is one CDN file behind `k_bsCssUrl` and `base.htm`'s own `<style>` is six lines of theme tokens written into Bootstrap's variables. Nothing there to split.
  - Where it pays off is a kit whose components bring their own presentation. The nearest one is Orbit's `dash-*` set, whose rules currently sit in `orbit/components.htm`'s static block mixed with the page's own; making those four reusable would give each its own stylesheet, and a page wanting only `dash-stat` would stop shipping the chart and dot CSS. Same for anything built ON the Bootstrap kit rather than wrapping it.

- [x] `<:define>`/custom tag instantiation -- implemented 2026-08-13. `<:define tag="name:base-tag">` becomes an inert `<template data-markout="...">` wrapping the base-tag element (stage1-load.ts's `expandDefine`, run inline inside `load()`'s own walk -- NOT as a separate pre-pass, since `load()` never descends into `template.content`); usage sites (e.g. `<theme-switcher />`) are detected in a post-pass (`expandCustomTagUsages`, after `page.customTags` is fully populated) and replaced with a `-u{scopeId}` comment marker. Every usage instance is compiled as a direct child of the root `page` scope (regardless of where it's physically nested in the DOM) -- this is what makes `$parent`/named-scope lookup "just work" with zero runtime scope-walking changes (a definition's own expressions only ever see `page`/`global`, plus anything reachable as an ordinary named-scope value like `head`). At runtime, `WebScope.acquireUsageDom()` + `WebContext.findElementById`/`findUseMarker` do a whole-document (not parent-scoped) search to find/clone the definition's stencil and replace the marker, mirroring SSR-hydration-reuse-by-id the same way `:for-each` clones do.
  - Known gaps (not yet addressed): `stage4-resolve`'s `validateDeps` checks a definition's OWN (naturally-nested, more permissive) scope location, not the runtime's actual page/global-restricted view -- a narrow compile-time-validation/runtime inconsistency. `scope.children = defScope.children` (reference-shared across all usage instances) is unsafe if a definition contains nested child scopes with their own ids (fine for a flat definition like README's example, a real gap for nested ones). Attribute-collision handling (usage-site attributes colliding with definition-provided ones) isn't addressed.
  - Along the way, found and fixed two unrelated pre-existing bugs this surfaced: (1) `preprocessor.ts`'s raw `childNodes.splice()` calls (import/group flattening) never updated the moved nodes' `parentElement`, so anything relying on it (like `expandDefine`'s `insertBefore`) operated on the wrong, stale parent. (2) `stage1-load.ts` inserted DOM_TEXT_MARKER comments around interpolated text uniformly, including inside atomic/raw-text tags (`<style>`/`<title>`) -- real HTML parsing can't preserve comments as distinct siblings there (HTML spec 13.2.5.1: it's all one raw text node), so the markers leaked into the served CSS/title text AND desynced `WebScope`'s marker-indexed `this.texts[]` array for every text value after the atomic one in the same scope. Fixed: no markers for atomic-tag parents; `WebScope.init()`'s scan now recognizes an atomic-tag container directly (`DOM_ATOMIC_TEXT_TAGS`) and pushes its one unmarked text child in the same document-order position a marker-delimited entry would occupy.

- [x] parenthesized interpolations -- fixed 2026-08-12. `${(1 + 2)}`, `${({b: 1})}` and friends didn't work: acorn's `parseExpressionAt` drops parentheses by default and reports the INNER expression's end, so `parseExpression` handed callers a position pointing AT the `)` where they expected `}`. Fixed by parsing with `preserveParens: true` (so the node's range spans the parens) and stripping the resulting `ParenthesizedExpression` wrappers before returning -- they're an acorn extension, not ESTree, and estraverse has no visitor keys for them while escodegen couldn't print them. The outermost wrapper's range is kept on the unwrapped expression, since that's what callers read to find the closing `}`.
  - The two halves failed differently, and the quiet half is the interesting one. Attribute values (`parseUnquotedExpressionValue`, `parseQuotedValueExpression`) reported "Unterminated attribute expression" -- wrong, but loud. The two TEXT paths (`parseSplittableText`, `parseAtomicText`) instead did `if (s.charCodeAt(j1) === REXP) { j1++ }` with no else, so on a mismatch they just didn't advance and the leftover source spilled into the page as literal text: `<p>${(1 + 2)}</p>` rendered `3)}`. Both text paths now report "Unterminated expression" rather than walking past a missing `}` -- same rule as stage4: never treat "didn't match what I expected" as a no-op.
  - Note this was reachable from perfectly ordinary source: `${({a: 1})}` is the natural way to write an object literal in an attribute, and `${(a ? b : c)}` is just defensive parenthesizing.

- [x] runtime error handling -- done 2026-08-12. Every failure now funnels through `CoreContext.onError(phase, err, value?)`, carrying the owning scope id and value key, so a message names the binding at fault (`markout [update] s3.text$0: ...`) instead of pointing into runtime internals. De-duplicated per `(phase, scope, key, message)`, so an expression throwing every cycle reports once.
  - The worst case was `link()`'s `catch (ignored) {}`: a dep resolving to nothing was 100% silent, and its only symptom was a binding that never updated again -- the exact failure class just fixed at compile time, still fully alive one layer down. Verified before/after with a hand-built props tree carrying a dep on an undeclared name.
  - **Semantics change**: a failed expression now yields `undefined`, never its previous value. Keeping the old one made a binding's contents depend on which earlier evaluations happened to succeed, and showed stale data as current.
  - `applyPending()` was unguarded: one throwing callback aborted the whole flush, skipped the remaining callbacks AND skipped `clear()`, leaving `pending` dirty into the next cycle. Each callback is now guarded individually and the batch drains in a `finally`.
  - `propagate()`'s catch was unreachable (everything inside is already caught by `update()`); it reports rather than swallows now, with `finally` keeping `pushLevel` balanced.
  - Dev mode: `markout <dir> --dev` (also `Server({dev})`). The two halves are handled differently on purpose. SSR failure -> the server serves a page built SOLELY from the errors (HTTP 500), with no content and no runtime: the rendered page is already wrong, and shipping it would just send the browser off to run the same expressions against the same initial values and fail identically. Post-hydration failure -> `WebContext` appends to a `<ul id="markout-errors">` panel in the page; the flag reaches the client via `window.__MARKOUT_DEV`, emitted by stage7 next to the props. Without `--dev` the page is served as rendered and errors go to the server log only -- a failing expression shouldn't cost a production page its runtime.
  - First attempt built the error report by MUTATING the compiled page (stripping its own bootstrap `<script>`s after SSR, via a `Page.bootstrapScripts` list). Replaced on review with a blank page built from the errors alone -- no IR bookkeeping, no mutation of compiled output, and it matches how compile errors are already served. Also made the panel's SSR->client de-duplication unnecessary: SSR never paints now, so the browser can't inherit a panel, and `onError`'s own de-duplication already guarantees distinct rows.
  - The only remaining `catch (ignored)` in the runtime is in `showError` itself, where it's correct: the error has already been reported through the normal channel, so failing to paint the panel must not cascade.

What was wrong was the `slotted: true` stage1 emitted for the runtime: it was set on EVERY custom-tag usage anywhere inside slotted markup, not just one sitting directly in the slot.
