- [x] `markout build <docroot> <outdir>` -- ahead-of-time delivery as static assets. Implemented 2026-08-17 in [build.ts](packages/core/src/build.ts), which moved from the CLI to core in 2026-08.
  - Why it outranked the language work: the CLI served and never wrote, so Node in the request path was the only way to deliver a page -- and the audience [POSITIONING.md](POSITIONING.md) names as the beachhead, server-rendered Rails / Django / Laravel / PHP shops, is precisely the one that cannot add a Node process in front of its app. Not a convenience: it is what makes the stated audience addressable at all.
  - Not client-side rendering: the same `renderPage` the middleware runs per request, run once per page at build time, so the markup is in the file and a page's static content does not flash in after the runtime loads. That is the property that distinguishes this mode from Alpine rather than merely matching it, and the CLI test asserts the resolved value is in the output.
  - `DEFAULT_RUNTIME_SRC` stopped being dot-prefixed, becoming `/markout-runtime.js` in BOTH modes -- the bundle's own filename on disk. The dot was sound while the middleware ANSWERED the path, since then it is never a file and cannot be shadowed by real content; it stops being sound the moment a build makes it a real file on somebody else's host, because a dot is what hosts use to decide a file is not for publishing (GitHub Pages runs Jekyll, which drops dotfiles without a `.nojekyll`; denying dot-paths is common hardening). Two names for one artifact was considered and dropped: one name, and the plain one, since the failure it risks (a docroot file shadowed while serving) is detectable and the one it avoids is a 404 on every page of a host you do not control.
  - The shadowing that buys: `markout()` warns at startup when the docroot holds a file at that path, and `build` refuses outright rather than copying it over the runtime it had just written -- which it did, reporting success, with every page in the output broken.
  - A compile error exits non-zero with `file:line:column: message`, because this is the half of the checking a static host can never do later: a served page reports its errors to whoever asks for it, a built one is read by somebody who cannot see the console. A RENDER error does not fail the build, matching what the server does with the same failure.
  - `-p/--page` needed `enablePositionalOptions()`, not just a subcommand. Commander matches an option against the PROGRAM wherever it appears, so `build src out -p index` handed `-p` to `--port` and the build silently saw no page -- it compiled everything and copied every asset, which looks like success.
  - Symlinks are followed. `kits/bootstrap/std-kit` is a link to the kit next door, and a linked directory is neither a file nor a directory to `readdir`, so trusting the dirent copied a directory as a file (`ENOTSUP` on the first real docroot tried).
  - Assets: everything that is not `.html`, `.htm` or dot-prefixed is copied, which is what `express.static` already serves from the same directory. That means a docroot with source in it publishes it -- the site's own `server.ts` lands in the output (`orbit-db.ts` did too, until Orbit stopped having a back end). Faithful to the served mode and still a footgun, which is why the report prints the extensions it copied rather than only a count. Whether `build` should refuse or exclude known source kinds is undecided; a denylist invented here would be arbitrary.
  - Dot-prefixed names: skipped, except `.well-known/`, `.nojekyll` and `.htaccess`, which a deployable needs. An ALLOW-list because the two sets differ in kind -- what a host must serve is short and standardised (RFC 8615 for the first), while what must never be published grows with every tool installed and includes `.env`. `/.well-known/` is served too, which the blanket `/.` refusal had made impossible: a certificate could not be issued for a docroot markout was serving. It needed its own `express.static` mount, since declining the path is not enough -- static will not serve a dot-path on its own. `.nojekyll` and `.htaccess` are copied but NOT served: a host reads those, a client never asks for them.
  - Found while verifying that: `markout <abs-path>` appended an ABSOLUTE docroot to the working directory (`path.join(cwd, pathname)`), so it watched and served `$PWD/srv/site` and answered 404 for the whole docroot. Pre-existing; `build` used `path.resolve` from the start, which is how the two came to disagree.

- [x] a build that refuses what it cannot deliver -- done 2026-08-17. A `:server-` value that fails now FAILS `markout build`, and its page is not written.
  - The rule, and why it is that rule: whether the browser can repair the failure. An ordinary value that throws while rendering is re-derived there and may well succeed -- `${user.name}` asked before its datasource answered is the everyday case, and the served page is fine -- so a build warns. A `:server-` value crosses FROZEN, with a result and no expression, so nothing re-runs it: whatever it failed to produce, the page is without permanently. `RuntimeError.serverOnly` carries the distinction, set in `CoreContext.onError` from the value that failed, because phase cannot tell them apart -- a rejected promise (`settle`) and an expression that throws outright (`update`) are both this kind.
  - NOT the compile-time refusal of `:server-` values this entry used to plan, and the reason is worth keeping: a value that reads nothing of the request works perfectly well at build time, and baking its answer into the markup is what static site generation IS. Whether a given value needs a request is also decided at runtime -- `std-data` holds the same `:server-` value whether it is inert or a fetch, depending on `:client` -- so no static check could separate them. The render can, and the build runs one.
  - Two `std-data` fixes came with it, and the first was a real defect: `:_url` resolved `:url` against `$origin` unconditionally, so `new URL('/d.json', undefined)` threw when there was no origin. That value is computed whether or not the fetch happens, which meant `:client` -- the mode documented as the way to have data in a BUILT page -- was itself unbuildable. It now leaves a relative url alone, which is right anyway: the browser re-derives it against a real `location.origin`.
  - The second: a served datasource with a relative url now REJECTS with a message naming the fix, instead of the page rendering blank. Deliberately unlike a 404, which this component carries back as a value on the grounds that it is a fact about the page's data -- "there is no server here" is not that. It is the datasource being written for a delivery this page is not getting, which only the author can fix, so it is said where the author will see it. Building Orbit went from nine `Invalid URL` warnings and a silently dataless page to nine sentences and a non-zero exit.
  - Still open, and unchanged by this: whether one docroot can produce both, or whether a page declares which mode it is for. What is fixed is that a page which works in only one of them says so at build time rather than at a visitor's first paint.

- [ ] a build whose data was simply not there
  - Noticed 2026-08-17 while verifying the entry above, and left alone deliberately. `markout build` with an ABSOLUTE `:url` fetches while the page is built, which is the static-generation case worth having -- and if that fetch fails (the API down, a 500, DNS), `std-data` carries the failure back as its `error` value, nothing is reported as a render error, the build exits 0, and the page ships with the error in it instead of the data.
  - Which is the component's own rule, and the right one for a SERVED page: a 404 is a fact about the page's data rather than a fault in the render, so it reaches the page instead of a log the visitor cannot see. A served page is also rendered again on the next request, so the bad answer lasts seconds.
  - A built page is final, and that is the whole difference. An API that was down at 3am produces a deploy where every page says so, with a green build behind it -- the same "quietly wrong" shape the `serverOnly` rule just removed for a relative url, surviving in the absolute one.
  - The candidate fix, which would keep served behaviour identical: `std-data` rejects rather than carrying an `error` when the fetch fails AND there is no `$origin` -- the same signal the current fix reads, since no origin means no request means nothing will render this page again. It is a build failure exactly when the answer cannot be retried.
  - What makes this more than a `std-data` detail: "is this render final?" is not something a page can ask. `$origin`'s absence approximates it, and reading an approximation is how a component ends up encoding a delivery mode it was never told about. If pages are ever to adapt deliberately, that primitive is what the entry above is really asking for.

- [ ] markout services, and the SSR shortcut they would make sound
  - A datasource reaches its data by URL, so the same component works in the browser and while rendering. That is the point of `std-data` and it is what makes it convincing as an ordinary component -- but server-side it means the page fetches its own API over HTTP from inside the process serving it.
  - Measured on Orbit 2026-08-17, when it still had an API of its own (see the entry at the top of this file; the numbers stand as a measurement of the shape, not of any page in the repository today) (one shared db instance, the two modes alternated so warm-up favours neither): the render costs 70.6ms with its sources over loopback HTTP and 54.4ms with them answered in process, so the hop is 16.2ms of it. Only ~4ms of that is HTTP framing -- nine parallel loopback fetches cost 25.4ms against 21.2ms for the same nine db calls, and the db IS the 21ms. The rest is the settle waterfall: `incidents` cannot be asked for until `services` answers, so the render pays round-trip latency twice, through the whole Express stack each time.
  - Interception would work and needs no page changes. `renderPage` can inject a per-render `fetch` through `addedGlobals`, which override the built-ins in CoreGlobal -- scoped to one render rather than patching a global, which matters now that different pages render concurrently -- and the middleware can reach its own app through `req.app` and dispatch a synthetic request in process. Same-origin shortcuts, everything else falls through.
    - It would have to KEEP the JSON round trip. Skipping it looks like free savings and is not: the browser receives a `Date` as a string, so a shortcut that hands over live objects gives SSR richer types than the client, which is the exact divergence the HTTP design exists to prevent. It costs 0.3ms.
    - And it should be opt-in rather than automatic, because it reintroduces a server-only path for data loading. When it diverges -- middleware ordering, a header, a route that treats a synthetic request differently -- the bug appears only in SSR, which is the worst place to look for one. One flag to flip makes "is my datasource lying to me" a one-step answer.
  - The version worth building instead: a datasource declared as a markout SERVICE rather than as an arbitrary URL. Then markout owns both ends of the contract and the shortcut is sound by construction rather than by interception -- no synthesized requests, no hoping Express behaves the same both ways. It would also allow what interception cannot: knowing which services a page needs before the render starts, and so collapsing the waterfall that costs more here than the transport does.
  - Not urgent. 16ms on a page that renders in 70, against a change that touches how data reaches a page in one of the two environments it has to reach it in identically.

- [x] server-only values — `:server-name=${expr}` means "this expression runs on the server only; the client receives its result". Implemented 2026-08-16; design and decisions in [docs/design/value-transfer.md](docs/design/value-transfer.md), user-facing docs in [syntax.md](docs/reference/syntax.md#server-only-values).
  - Motivation is three classes of value hydration currently gets wrong: state assigned imperatively (a fetch payload exists nowhere in the served HTML, so SSR'd content is *wiped* on hydration), values derived from server-only inputs (file, env, DB, session), and non-deterministic ones (`Date.now()`, `Math.random()`) which don't break but visibly flip.
  - The value is **frozen** client-side — it arrives with `val` and no `exp`/`deps`, the inert shape `CoreGlobal` already uses. Freezing is correct for all three classes, not a compromise. The usage rule that follows: **keep the source, never the derivation** — mark `:server-user=${loadUser()}` and let `:greeting=${'Hi ' + user.name}` re-derive, or pinning the derivation silently decouples it.
  - **Two globals**: `__MARKOUT_PROPS` (app descriptor, function of the source, cacheable) and `__MARKOUT_STATE` (this render's state, per-request, never cacheable). Fusing them was considered and rejected: it costs a second full `escodegen` pass per request, mixes third-party bytes into the same script as all generated code, and closes the door on caching the expensive half. Nothing caches today, which is what makes the per-request half safe — and the split is the constraint any future page cache has to respect.
  - Format is a **JS object literal, not JSON**, so `undefined` (load-bearing: a failed expression yields `undefined` and never `null`), `Date`/`Map`/`Set`/`BigInt`/`NaN`/`-0` and cycles all survive with no tagged encoding. `JSON.parse('…')` parses ~2x faster and is the right trade only at hundreds of KB; deferred deliberately.
  - Escaping becomes security-relevant once a fetched payload lands in a `<script>`: `escapeScriptClose` handles `</script` but not `<!--`, and it was written for compiler-generated code, not hostile data.
  - Refusals landed in stage1 rather than stage2 as designed: stage1 is where the family prefix is determined, so the check costs one `if` next to the information instead of re-deriving it from compiled names.
  - Stencils are skipped when collecting, which the design missed: a `:for-each` host's values are prototypes for its replicas and are never evaluated, so collecting there sent `undefined` standing in for "never ran" — one spurious entry per list, and one per page for any `:for-data` not showing.
  - Name is still open — `:server-` describes the plumbing, not the contract. `:server-`/`:pin-`/`:once-` are closer. Now documented, but it is still one constant plus its refusal messages.

- [x] pending-work registry + async `renderPage` -- implemented 2026-08-16, and smaller than designed: there is no registry API. A `:server-` value whose expression returns a promise IS the registration, so a datasource is `:server-data=${fetch(src).then(r => r.json())}` with no new page-facing syntax. The rule that falls out: **async is allowed exactly where the result can be sent** -- an unmarked value's promise would have to resolve in the browser too, and hydration is synchronous. This also disposes of the `.json()` hole the design warned about, since what is awaited is the value's whole expression rather than `fetch`'s own promise.
  - **The runtime filters promises out of the reactive system.** A server value whose expression answers with a thenable holds it aside (`CoreValue.pending`) and reads as `undefined` until it lands. The first cut let the promise BE the value, and every problem after that came from there: a promise is truthy so guards passed and built requests out of `[object Promise]`, it has no `.length` so dependents threw, and rendering one printed `[object Promise]`. Pages are written against data; `undefined` is what "not there yet" already means everywhere else here.
  - Ordering survives as a smaller rule -- a value is not settled while one of its own sources is pending -- which still matters for an unguarded chain (`${Promise.resolve(a * 10)}` computes `NaN` before `a` lands). Guarded chains no longer need it.
  - Orbit (`kits/bootstrap/orbit.html`) is the end-to-end demo: ten `std-data` elements call its own API while the page renders, and the served console is complete. Nothing else in that page changed when its data stopped being a literal -- same filters, same charts, same tables over the same arrays. It brings its own express app (`kits/bootstrap/server.ts`), which is the truer picture anyway: an application has routes, and markout is the middleware that renders its pages.
  - Orbit is four files (`orbit.html`, `orbit/components.htm`, `orbit/sources.htm`, `server.ts`), split to show the shape an application takes. Components are imported, sources included -- a definition wants to arrive once per page however often it is named, an instance wants splicing exactly where it is written, since that is where its name resolves. `sources.htm` carries `:apiBase` on its root to show the token pattern is not a kit privilege.
  - One request per SET OF INPUTS. A value with sources re-evaluates whenever it is read in a new cycle, and settling anything opens one, so a server value whose request was in the air got asked again and again for the same thing -- ten sources, twenty-one requests. First fix was "don't re-evaluate while pending", which was too blunt: it also blocked the re-evaluation an unguarded chain depends on (`${Promise.resolve(a * 10)}` stayed NaN), and that silently made the settle loop's ordering rule inert. `CoreValue` now snapshots its sources' values when it starts a request and re-runs only if one of them moved. Kept for server values only, so ordinary values carry none of it.
  - NOTE the server-globals feature (`markout({ globals })`) is no longer exercised by any page now that Orbit goes through HTTP. It stays fully tested in `test/server/server-globals.test.ts`, but there is no demo of it -- worth one if a page ever wants in-process services rather than an API.
  - `renderPage` discards the whole first reading and takes it again once results are in, keeping only `settle` failures. A dependent still evaluates once before its sources arrive, and `${rows.length}` on `undefined` throws just as surely -- that is a value asked too early, not a broken page. Without this, dev mode replaced the page with an error about a value that was fine a millisecond later, which is how it was found.
  - Two limits, because they catch different things: a 5s deadline budgeted across the whole render (a slow network), and a 5-round depth cap (a page whose values feed each other too deeply, which would otherwise stall to the deadline on every request while reporting nothing but slowness). Either way the value becomes `undefined`, is reported under a new `settle` phase, and the page is still served.

- [x] `:if` -- added 2026-08-16. Truthiness, no item binding. The kit and Orbit's 28 conditions are now `:if=${cond}`, having passed through `:for-each=${cond ? [1] : []}` and `:for-data=${cond || null}` on the way.
  - The name was free because the language already refused it: a value has to be something an expression can say, and `${if}` does not parse. So a reserved word is a namespace no page can occupy, and a directive can take one with no prefix and no possibility of collision. The rule a reader ends up with is "if you could have declared it, it is a value".
  - Not every word that looks reserved is: acorn takes `let static async await yield of get set from as` as identifiers in sloppy mode, so those are NOT safe to claim -- a page can declare them today. The safe set is `if else for while do switch case default break continue return function class extends super this new delete typeof instanceof in void var const try catch finally throw with debugger import export null true false`.

- [x] `:aka` and `:slot` are literal-only -- 2026-08-16. They are the two system attributes spelled as ordinary identifiers rather than reserved words, kept that way deliberately: no reserved word reads as well (`:this` for `:aka` is close; nothing covers `:slot`, since `:in` is the only reserved preposition left and it is vaguer). The price of that choice is that a page cannot declare values of those names, and the point of the error is to make the price visible -- `:slot=${x}` used to stringify the expression, address `[object Object]`, match no slot and drop the content in silence.

- [x] `:else-if`/`:else` -- added 2026-08-19. Both compile to the same `if$` value `:if` does, since all three answer one question at one arity; what they add is a link to the branch before them, and the rule that the first condition to hold takes the position. `:else` is free for the reason `:if` was (a reserved word no page can declare), `:else-if` for a different one (a dash, which a plain value name cannot contain, and no `else-` family to claim it).
  - Sibling adjacency was the objection, and it turned out to cost one variable in the loader's child walk -- the question is only unanswerable AFTER loading, once every branch has been wrapped in a `<template>` and no element is next to what it was written next to. The rule is stated in the errors rather than left implicit: an `:else` needs a branch on the element immediately before it, and whitespace and comments are the only things allowed in between (anything that renders would appear between two alternatives at most one of which is showing).
  - Chosen over a value-graph chain, which would have needed dependency edges between sibling scopes -- machinery the compiler has none of, since `via` navigates only to `$parent` and named scopes. The runtime instead re-decides the whole chain from whichever branch's condition moved, which is what the graph could not do anyway: the branch that has to give up its position is exactly the one that did not change, so nothing would ever wake it.
  - Links are compiled as sibling ids (`elseOf`/`elseNext`), not references, which is what makes a chain inside a `:for-each` work -- a replica shares its host's child props verbatim, so every replica's branches carry the same ids and each finds its neighbour in its own copy. A lone `:if` carries neither prop, and takes exactly the path it took before.

  - **Layer 2 shipped in std-kit after all -- 2026-09-01, and point 3 below was revisited to do it.** `std-router` / `std-route` / `std-params`: routing on the query string, nesting through `$outer`, resolved while rendering so the response is already the right screen. Level 2 in the navigation doc is now this rather than a fragment. Point 3 argued a router must be a kit of its own because a router is a design SPACE and std-kit's surface is effectively the language's -- and that argument still holds for the router it was written about. What was built is the other thing: exact names, no patterns, no ranking, no guards, no lazy loading, and the space itself declined and left to the advanced kit. That is nearer `std-data`'s "fetch a url, hand back what came back" than to a framework's router, which is what made it safe to be ambient. The two items above are the boundary, stated so the line is a decision rather than a gap.
  - **`$outer` shipped with it**, the third of the five primitives that document lists, and for the reason the other two arrived: it is worth having on its own terms -- a field finding its form, a tab finding its tabset -- and routing is one caller rather than the reason. Two remain: a render handing its state back to the build, and comptime `:if` folding, both of which the enumerating render needs and neither of which anything has yet asked for.
  - **Why stop there.** Routing is a design space and every framework that guessed early rewrote it later; the two levels that work carry no guesses. The remaining primitives (a render handing its state back to the build, comptime `:if` folding, `$outer`, `$aka`) are the expensive and least-validated ones, and the fragment level is now the cheapest way for a real application to say what shape layer 3 should be. See docs/design/advanced-router-kit.md.
  - **And the level 3 order, when it resumes**: path routes over real files plus Navigation API interception first -- that needs no enumeration, no `:if` folding and no build change, and it fixes what level 2 cannot (the response is right, so unfurlers and JS-less readers are too). Synthetic routes (`/user/42`, no file behind it) are what need the whole apparatus.

  The original entry follows. Nothing anywhere -- docs, POSITIONING, the site -- answers "what happens when my app has more than one page", and the multi-page answer is defensible with numbers behind it (an ordinary page compiles in ~2ms, the heaviest page here in ~111ms, and the middleware caches the compiler's output so a page compiles once per edit rather than once per request) -- but an unstated position reads as an oversight rather than a decision to anyone arriving from an SPA framework. What answers it is a component, because a component answers by existing.

  1. **Reading the page's own URL: the language.** `$origin` is the origin and nothing else, and the globals list refuses `location` because a browser-only name makes an expression that works in one half of an isomorphic render and throws in the other. But the path and the query are not headers or cookies: the server has them from the request, the browser has them from `location`, and they mean the same thing on both sides -- exactly the bar `$origin` clears. No router of any design can be written without this, it carries no opinion, and it is not kit material. Needs designing and naming (`$url`? a path and a search?) before anything else here can start. The middleware already holds the value: `renderPage` is handed `origin` and nothing else.

  2. **The address bar as read/write state: `std-kit`.** Reading is a global; NAVIGATING is a side effect with a lifetime -- a `popstate` listener to attach and detach, and state to hold. That is exactly the criterion std-kit's own README sets for what belongs in it: "`<stdio.h>` is the half that genuinely needs a scope, a lifetime and somewhere to keep state." One sensible design, which is what makes it safe to be ambient.

  3. **The router: a kit of its own.** Settled, and the reason is opinion rather than cost. `std-data` is "fetch a url, hand back what came back" and is barely a design decision; a router is a design SPACE -- exact versus pattern, nested versus flat, guards, hash versus history, scroll restoration, lazy loading. std-kit is spliced into every page by core and peer-depends on it, so its surface is effectively part of the language's: shipping one routing opinion there would make it THE opinion, in a project positioned as not an application framework, and a wrong ambient component is a migration where a wrong package is a version bump. `bootstrap-kit` is separate for precisely this reason, and routing sits beside it on that axis rather than beside `std-data`.
    - The cost argument was considered and does NOT support this, which is worth recording so nobody re-derives it: an ambient part costs ~1ms per page per COMPILE (measured: 0.8ms -> 1.8ms on a trivial page with std-kit spliced), and the middleware caches compiled pages, so that is once per edit in dev and once per process in production. Noise. The decision rests on where opinions may live, not on what they cost.

  - **Two different things wear the word, and only one is in scope above.** *In-page* routing is "which region of THIS page is showing, decided by the URL" -- `:if` over a value plus history, and layers 1 and 2 are most of it. *Between-page* routing is replacing the document without a round trip, which is the SPA question: a compiled page is one document, and swapping one for another is a mechanism markout does not have and may well not want. Worth deciding the second explicitly, because building the first will make people ask.

  - Layers 1 and 2 are worth building even if the router never is. They are what would let the desk demo's `?q=` survive a reload, which is a real gap today and needs no routing opinion at all.

  - No prior art here to copy: the desk demo looks like some and is not. Its `?q=` builds the DATASOURCE's url out of a page value; `location` and `history` appear nowhere in it. Its comments say so now, in all three places that used to say "the URL".

- [ ] path-shaped URLs, which is the one thing `std-router` gives up on purpose. It routes on the query -- `?about/team` -- because that is what costs nothing: `?about` and `?index` are the same file, so any host serving static files already serves every route, and the response is already the right screen because the query IS sent where a fragment is not. `/about/team` reads better and is what a reader expects to paste, and the price is the configuration the query design exists to avoid: either the host rewrites every unmatched path to one file (an nginx `try_files`, a `_redirects`, a Pages `404.html`), or `markout build` writes a file per address -- which needs the enumerating render, the one piece of layer 3 that is genuinely expensive and still unsettled (see the open questions in [docs/design/advanced-router-kit.md](docs/design/advanced-router-kit.md)). Worth being clear that this is not a missing feature of the basic router but the boundary it was drawn at: a site that wants pretty paths and will configure a host for them is asking for the advanced kit, and a site that will not is better served by the query.
  - What it must not do is arrive as a flag on `std-router`. "The same component, but now your host needs a rewrite rule" is a property no ambient part should be able to acquire by an attribute, because the failure lands on a deploy rather than on a page.

- [ ] parameter matching -- a route that matches a SHAPE rather than a name. `?user/42` selects a route called `42` today, which is useless, and `std-params` covers the case that is not (`?user&id=42`, named and read as `q.data.id`) -- so what is missing is specifically the positional one, and it is missing because it is a design space rather than a line of code. Everything arrives with it: a pattern needs RANKING against a literal that also matches (`/user/new` versus `/user/:id`), somewhere to put what was captured, and constraints (`::match=${/^\d+$/}`) so `/user/abc` fails at MATCH time rather than rendering a route that then cannot use its own parameter. Ranking in particular is what the "declarations, never conclusions" rule in the design notes exists to keep answerable: a route may read a peer's segment, never whether that peer matched, or A matches iff B does not and the graph has a cycle instead of an answer.
  - A smaller inconsistency in the same area, found while writing `std-params`: the router accepts `;` as a query separator, so `?user;id=42` names the page `user`, but `URLSearchParams` does not split on `;` (it stopped being a legal separator long ago), so `id` is unreadable. Nobody writes `;`, which is why it can wait -- but the two halves of one kit read the same string differently, and that is the shape of thing that is cheap now and archaeology later.
  - The cheap half is worth separating from the expensive one. Exposing the segments a router did not consume -- so `<std-route ::page="user">` could read what followed it -- needs no matching, no ranking and no constraints, and would cover "one id at the end" without entering the space. Whether that is a good idea or a trap that grows into the rest of it is the actual question.

- [ ] `$host` and `$outer` do not reach from a component's arguments, and the design notes' own idiom is written there. Both navigate structure, and a value's structure is the scope its expression runs against -- which for most markup is where it sits, and for a component's ARGUMENTS and for slotted TEXT is the call site, by the rule that makes `::title=${title}` mean "the title from out here" rather than the instance's own. Structure follows names there because one expression is evaluated against one scope. So `<other-tag ::what=${$outer('x')} />` written inside `<x>` reaches nothing while `<b :x=${$outer('x')}>` in the same position reaches, and the difference is whether the tag is a component. Pinned as a table of cases in `packages/core/test/render/outer.test.ts`, documented in [syntax.md](docs/reference/syntax.md), and worked around in the router demo by putting the expression on an element.
  - Fixing it means a structural builtin resolving from the DECLARING scope while names still resolve at the call site -- a per-value indirection where there is currently one scope per expression, and a scope allocated per call-site value on a page that may hold ten thousand of them (the `:buy=${add}` benchmark is exactly that shape). Cheap workaround, expensive fix, so it is a question rather than a task.
  - It also means [docs/design/advanced-router-kit.md](docs/design/advanced-router-kit.md) §9's `<rt-data ::url="${$outer('rt-route').param}" />` needs restating before anyone builds from it. The caveat is in the document; the idiom is not yet rewritten.

- [ ] `:switch`/`:case`/`:default`, postponed. All three names are reserved, so they are available on the same argument as `:if`. Now that `:else-if`/`:else` exist it has to earn its place against them rather than merely against `:if`: cases are CHILDREN of the switch, so the subject is written once and the branches nest visibly, where a chain repeats `n ===` per branch and holds together by adjacency. Decisions if it happens: strict equality like JS, first match wins with no fallthrough, `:case` must be a direct child, guards come free via `:switch=${true}`, and a non-matching branch evaluates nothing. Cost: it needs a container element, which the chain does not -- much cheaper now that `<:group>` renders nothing and already takes the branch attributes, and in one case it is not a cost at all (below).
  - What earns its place, found while exploring [scoped slots](docs/explorations/scoped-slots.md). Two arguments the postponement did not have. **The cheap alternative is the expensive one:** short-circuiting the existing chain looks like the fix that needs no new syntax, and is not -- `decideBranch` keeps every condition linked and evaluates all of them each pass ON PURPOSE, because the branches are deliberately not dependencies of one another, so suppressing later evaluations means either adding edges between branches (more graph, not less) or giving `CoreValue` a dirty-but-not-evaluated state, which is a change to the settle loop's invariants. A directive family is the cheaper route to the same win, which is not how that trade usually goes. **And the container becomes the point rather than the price** where a chain has a binding to declare: a scoped slot's `:slot-as` has no home on a chain and ends up on whichever branch happens to be written first, where `<:group :slot-as="cell" :switch=${cell.column.key}>` declares it once, in the right place.
  - Undecided, and the performance argument rests on it entirely: **whether `:case` takes a literal**, like `:aka` and `:slot`. "A non-matching branch evaluates nothing" is about the branch BODY, which is the weaker property. What makes a switch cheaper than a chain is one reactive value for the subject plus N literal comparisons, against N conditions each with its own dependency edges -- so `:case=${expr}` would put every one of those values back and leave the chain re-spelled rather than improved. Worth noting the magnitude honestly either way: ~640 values against ~160 for a 20x8 table with five branches, which is nothing at either end. It is a large-N story, and large N is where this repository has been bitten before -- see the `for$each`-on-replica guard, whose N wasted links and N wasted re-evaluations made a 10k-row mount OOM.

- [x] a name inside a region is read with `?.` -- 2026-08-19, replacing the outright refusal made earlier the same day. `${panel.field?.text}` compiles, reads `undefined` while the region is away and the live value while it is showing, and a change inside the region reaches the reader outside it. The guard is required, not merely permitted: without it the reference is still a compile error, now naming the guarded spelling.
  - The right shape because it is JavaScript's own: a thing that may not be there is `?.`, and no new concept had to be invented for a language whose stance is that expressions are expressions. - [x] a guarded WRITE into a region -- 2026-08-19, `$set`. Reading into a region is `panel.field?.text`; writing is refused, because `a?.b = c` is not JavaScript and a write that silently lands nowhere is the failure shape the read guard exists to remove. But optional chaining DOES cover calls -- `a?.b(c)` is perfectly valid -- so a system function is the spelling that needs no new syntax: `panel.field?.$set('text', v)`, alongside `$value`, `$parent`, `$id`, `$host` and `$dom`. It takes one name, not a path. And the `?.` IS still required -- consistency won over reading better, since a `$set` that looks guarded and is not would be the one shape this feature exists to remove.

It is checked against the scope the chain landed in, the same way a segment is.
  - It is a write, so it records no dependency -- subscribing a value to what it assigns would have it re-evaluate itself.
  - Plain assignment into a region is still refused, and now names `$set` instead of saying a write cannot be guarded, which stopped being true.

- [ ] `markout build` compiles pages one at a time, and could use a worker pool. Its loop is compile -> render -> write per page, sequentially; the comment gives the right reason for serialising RENDERS of one page (they write into that page's document) but the pages in a build share nothing, so there is nothing there to contend over. Measured on this site 2026-08-19: 16ms for the homepage, 80ms for the kitchen sink, 111ms for Orbit, so a docroot of any size is close to linear speedup for free. The interface fits a worker in a way the SERVER's never will -- pathname in, file written out, nothing live crossing the boundary -- which is the whole reason this is worth doing there and not there.
  - Not for the middleware, and not for want of effort: what a compile produces is a live object graph (a server DOM, scopes, values, acorn ASTs) and the point of caching it is that `renderPage` writes into that document. None of it survives `postMessage`, so a worker could only return serialised HTML and the props string -- and rebuilding something renderable from those is the compile again, in the place it was being moved out of. The server's exposure is one compile per page per invalidation anyway, which a warm cache makes rare and `pageLimit` bounds.
  - Two things to settle first. Each worker pays its own kit discovery and module load, so there is a crossover below which a pool is slower; measure it on a large synthetic docroot rather than guessing. And results have to be reassembled in pathname order rather than completion order, or `errors`/`serverErrors`/`runtimeErrors` come out in a different order per run and a build stops being reproducible.

That turns the most confusing failure in the onboarding path into a click.
  - Nothing is needed for publishing: `publishableSegment` already excludes every dot-prefixed segment, with `.well-known`, `.nojekyll` and `.htaccess` allowed through. Worth stating because the exclusion matters more here than it did for `node_modules` -- kit files are `.htm`, so a docroot of `.` without it would compile and serve every kit fragment as a page.
  - A central kits listing service is the obvious companion and should not be built first. `https://registry.npmjs.org/-/v1/search?text=keywords:markout-kit` already answers the question with no server, no uptime and no moderation burden; pair it with a curated `kits.json` in this repo for a featured section. A kit is code that runs at compile time in the user's editor, so the curated list should be the default view and searching the whole registry a deliberate second step.

- [x] the application-shaped gaps, and what is left -- 2026-08-30. `requestGlobals` (a global built per request, so an authenticated page server-renders instead of fetching itself back), `:server-status` / `:server-redirect` (a page saying what its response should be, read from `<html>` or `<head>` so a kit can ship one), and `:server-if` (a branch the server decides, so the one it did not show is not sent -- which is how `<div :if=${user.isAdmin}>` was shipping the admin panel to everyone). `renderPage` hands back the state it collected, which is router-kit's second primitive arriving early. The assessment of what is complete and what is not is in [LAST-MILE.md](LAST-MILE.md), items 6, 7 and the section after them.

- [x] `$url` in page scope -- 2026-08-30. The whole address the page is being rendered for, as a `URL`, on the same terms `$origin` is: supplied rather than discovered, from the request on the server and from `location.href` in the browser, because the value of the name is that the two agree. `$origin` is a strict subset and stays a name of its own -- a page wanting the origin should not have to reach through an address to say so -- and is now taken FROM `$url` when a caller passes only the address, so one fact is supplied once.
  - A `URL` instance rather than a path and a search: `URL` was already on `GLOBAL_NAMES`, so the shape needs no new type and `searchParams` arrives with it, which is the request-params half at no design cost.
  - Supplied by all four callers that know an address: the express middleware from `req.originalUrl` (not `req.url`, which a mounted middleware sees stripped of its own prefix), `hydrate()` for a test document whose location is the runner's, `browser.ts` from `location.href`, and `markout build` as the origin plus the page's own path when `--origin` said where the pages are going. An unparseable one is treated as none: a page whose address cannot be read is a page rendering without one, not a render that fails.
  - **Live, and the first global that is** -- 2026-08-30. A navigation that keeps the document moves the address, so `$url` is a dependency like any value: `stage4-resolve` emits one for it (a single segment, which `$value` resolves by walking the chain to the global scope from wherever it was written) and `browser.ts` follows `navigatesuccess`, or `popstate` where there is no Navigation API. That is the assumption the `$ua` notes below predicted would have to go -- globals were all built with `val` because "these never change", and one of them now does.
  - **And it cannot be written**, in whole or in part. `$url` is where the page IS, so assigning it would say the page had arrived somewhere it has not, and `$url.pathname = '/x'` would change the object and tell nobody -- both are refused with a message. NAVIGATING is the second layer's, per the split above: a side effect with a lifetime, written where it happens through `globalThis.location.assign(...)` until a kit offers better. This was built the other way round first, with a write asking the browser to go there; it read well and put layer 2 inside layer 1, and `$url = '/about'` is an assignment that assigns nothing, which is not what `=` means anywhere else in the language.
  - **Route params are a different feature** and belong with routing. `/tickets/:id` has no browser counterpart until something in markout owns the route table, and until then a query string is the whole of what a page can be asked. Worth saying when routing lands, because "request params" reads as both.

- [ ] `$ua` in page scope, a name of its own rather than part of `$url`. `$origin` already does this for one fact, and its comment in [core-global.ts](packages/core/src/runtime/core/core-global.ts) states the bar the rest have to clear: a name is offered when it means the same thing in the browser and on the server, and headers, cookies and method are refused because a page reading one renders something it cannot hydrate to -- and publishes a session while doing it. Decided 2026-08-29; nothing is built.
  - **A name of its own, because the two facts do not behave alike.** A single `$request` is honest on the server and a lie in the browser, and a single `$page` invites everything else about the page to be hung off it later -- but the real reason is that `$url` is a constant for the life of a render and `$ua` is not. Hanging a value that changes off the same object as one that does not would make "does reading this re-run my expression" a question about the property rather than about the name.
  - **`$ua` should be live in the browser, and that is what makes it worth having.** The string is the same on both sides -- `navigator.userAgent` and the `User-Agent` header -- so it hydrates cleanly, unlike a cookie. But the header is a guess and the browser knows the truth, so the browser's copy should keep answering: a `matchMedia` or resize listener calling `set()` on the global value, and every expression that read it re-runs through the ordinary cycle. Mechanically this is nothing new -- globals are already `CoreValue`s in `CoreGlobal` -- except that today they are all built with `val` rather than `exp` because "these never change". `$ua` would be the first global that does, which is a comment to fix and an assumption to check rather than a mechanism to write.
  - What `$ua` carries is then the open question, and it is bigger than the string. A raw UA string cannot be corrected by a resize, so a live value means derived facts -- coarse pointer, viewport class, reduced motion -- with the string underneath for whoever wants it. The server derives them from the header, the browser derives them from what it can actually see, and the two disagreeing is the normal case rather than a bug.
  - **The cost is a first paint that can be wrong.** A media query never guesses; a header-derived value guesses and is corrected after hydration, which is a visible re-layout. That says what the server half should do: pick the conservative branch, and keep `$ua` for what CSS cannot reach -- NOT RENDERING a desktop-only widget on a phone rather than hiding it, a payload decision and not a layout one. Worth saying in the docs, because the first thing anyone reaches for it for is the case a media query does better.
  - Downstream, markup that depends on the header needs `Vary: User-Agent` or a shared cache hands one visitor another's layout, and `markout build` has no request at all, so the static half has to render some defined no-agent branch and say which. The middleware's cache is of the COMPILER's output rather than the render, so at least that one is untouched.
  - A width tier came out of the same conversation and is the thing anyone actually wants -- nobody wants a UA string, they want to know whether they are narrow -- **and it is a component in `std-kit`, not a global.** Decided 2026-08-29. `$url` and `$ua` are language-level because they mean the same thing on both sides and carry no policy; a tier is a THRESHOLD TABLE, and a threshold table is a design-system fact. A global would make markout own Bootstrap's `576/768/992/1200/1400`, which is the "whose thresholds" problem solved by not having it: the numbers belong to whoever wrote the stylesheet, so they belong to a component the page configures. This is the same line [std-data](kits/std-kit/parts/data.htm) is on -- "an ORDINARY component, there is nothing about it the runtime knows".
  - **`:const-` thresholds make the table free.** Stage 5 substitutes a comptime value into its readers, so overridable breakpoints with Bootstrap's as the default cost nothing at runtime: the numbers fold into the comparisons and never ship as props. Compile-time is also the right LIFETIME for them -- a usage site cannot set one from a runtime value, and shouldn't be able to, since a breakpoint is an authoring fact and not a page state.
  - **[bs-theme-auto](kits/bootstrap-kit/parts/theme.htm) is the precedent, and it also answers the flash.** Its `<script :when-used="...">` runs before first paint precisely because the mode has to be on `<html>` before the first frame. The same script stamping a tier on `<html>` gives CSS a correct answer with no flash AND gives the reactive value a correct starting point in the browser -- without markout owning any of it. The `:when-used` half carries over intact too: a page that writes no tag ships no script, which is what makes this optional in the way the user is asking for.
  - **Which means it can ship before `$ua`, and gets better with it.** With no UA the server renders the stated default and the pre-paint script corrects it; that is already right for everything CSS can express. `$ua` only buys the STRUCTURAL case -- a `:if` deciding whether a desktop-only subtree is in the served markup at all -- where a pre-paint script is too late because the markup was never sent. So the two stack in the right order rather than blocking each other.
  - **The real cost of the component route is scope**, and it is the one thing a global would have done better. A global is visible in every expression on the page; a component's names resolve where it is written and below, which is why `std-data` tells authors to "put it at the top of the region that reads it". A page wanting the tier everywhere writes the tag at the top of the body and reads it from there. That is the ceremony this kit already asks for rather than a new one, but it is ceremony, and it is what makes `$widthSize`-as-a-global tempting.
  - **Refinement without a language release is the other half of the argument.** Tablets, pointer type, orientation, a watch -- each is a parameter on a component and a kit version, where as a global each is a change to `GLOBAL_NAMES` plus the compiler's copy in stage4-resolve kept in step by a test, shipped in the language, forever. Everything about this feature is going to be revised by contact with real devices, which is an argument about where it should live and not merely about how it should be spelled.
  - Still open: the tag name and what it exposes. `<std-width>` describes what it measures; `<std-viewport>` leaves room for the orientation and pointer facts that will want to live beside it. And a prerender still needs a stated default -- `md` is defensible for the reason a middle tier usually is, no visitor more than one step away -- with the same lean noted above: correcting DOWNWARD is cheap (ship bytes, drop them) and correcting UPWARD is not (construct what was left out, possibly fetching to do it).
  - **In `<head>` is where the instance should go, and it reads `head.`-qualified rather than bare.** A scope's name registers on the nearest enclosing NAMED scope (`CoreScope.nameSiteScope`), and lookup walks UP -- so a name written in the head is not reachable by a bare reference from the body: body's chain is body -> page -> global and never turns into head. It IS reachable as `head.<name>`, since stage1 gives `<html>`, `<head>` and `<body>` the built-in names `page`, `head` and `body` ([stage1-load.ts](packages/core/src/compiler/stages/stage1-load.ts)), so the head scope is a value on page like any other. Which is arguably the better answer than the alternative: `head.width` is spelled the same in every page that uses the kit, where a `:aka` at the top of the body is whatever each author called it. The `:logic` base tag makes the instance legal there -- it renders nothing and has no element, so nothing about it is head-specific except where its name lands.
  - And the qualification is worth having for a second reason, which generalises past this component: **the head is the kit's shelf and the body is the app's.** An app's own values are declared in the body and below, so a kit value that only answers to `head.` cannot be shadowed by one of them -- where a `:aka` at the top of the body can be, silently, by any nested `:width` on any element in between, for that subtree only. It also keeps the two namespaces legible in the source: a bare name is something this page declared, a `head.` name is something a kit supplies. Worth stating as a kit convention rather than as a fact about this one tag, since `bs-theme-auto` holds no value today only because nothing has needed one yet, and that is where its mode should land the day something does. Not enforced, and deliberately: a component that checked where it had been written would be the language knowing about a kit's convention, which is the coupling this whole item avoided by making the tier a component instead of a global. A documented best practice, and the failure mode for ignoring it is an unresolved `head.width` -- which names the thing that is missing rather than silently resolving to something else.
