- [x] `<:define>`/custom tag instantiation -- implemented 2026-08-13. `<:define tag="name:base-tag">` becomes an inert `<template data-markout="...">` wrapping the base-tag element (stage1-load.ts's `expandDefine`, run inline inside `load()`'s own walk -- NOT as a separate pre-pass, since `load()` never descends into `template.content`); usage sites (e.g. `<theme-switcher />`) are detected in a post-pass (`expandCustomTagUsages`, after `page.customTags` is fully populated) and replaced with a `-u{scopeId}` comment marker. Every usage instance is compiled as a direct child of the root `page` scope (regardless of where it's physically nested in the DOM) -- this is what makes `$parent`/named-scope lookup "just work" with zero runtime scope-walking changes (a definition's own expressions only ever see `page`/`global`, plus anything reachable as an ordinary named-scope value like `head`). At runtime, `WebScope.acquireUsageDom()` + `WebContext.findElementById`/`findUseMarker` do a whole-document (not parent-scoped) search to find/clone the definition's stencil and replace the marker, mirroring SSR-hydration-reuse-by-id the same way `:for-each` clones do.
  - Known gaps (not yet addressed): `stage4-resolve`'s `validateDeps` checks a definition's OWN (naturally-nested, more permissive) scope location, not the runtime's actual page/global-restricted view -- a narrow compile-time-validation/runtime inconsistency. `scope.children = defScope.children` (reference-shared across all usage instances) is unsafe if a definition contains nested child scopes with their own ids (fine for a flat definition like README's example, a real gap for nested ones). Attribute-collision handling (usage-site attributes colliding with definition-provided ones) isn't addressed.
  - Along the way, found and fixed two unrelated pre-existing bugs this surfaced: (1) `preprocessor.ts`'s raw `childNodes.splice()` calls (import/group flattening) never updated the moved nodes' `parentElement`, so anything relying on it (like `expandDefine`'s `insertBefore`) operated on the wrong, stale parent. (2) `stage1-load.ts` inserted DOM_TEXT_MARKER comments around interpolated text uniformly, including inside atomic/raw-text tags (`<style>`/`<title>`) -- real HTML parsing can't preserve comments as distinct siblings there (HTML spec 13.2.5.1: it's all one raw text node), so the markers leaked into the served CSS/title text AND desynced `WebScope`'s marker-indexed `this.texts[]` array for every text value after the atomic one in the same scope. Fixed: no markers for atomic-tag parents; `WebScope.init()`'s scan now recognizes an atomic-tag container directly (`DOM_ATOMIC_TEXT_TAGS`) and pushes its one unmarked text child in the same document-order position a marker-delimited entry would occupy.

- [ ] DOM-fidelity test gap, general (2026-08-13 retrospective): three real bugs in one session (`<template>.content` invisible to a plain `childNodes` walk, `parentElement` not fixed up after raw `splice()`, comments not surviving inside `<style>`/`<title>`) all trace back to verifying behavior via string serialization (`.doc.toString()`) instead of a real HTML parser. Worth auditing for more landmines of the same shape: foreign content (`<svg>`/`<math>` have their own parsing-mode quirks), `<textarea>`/`<xmp>` (also raw-text, not currently in `RAW_TEXT_TAGS`/`ATOMIC_TEXT_TAGS` -- does markout support interpolation inside them at all?), and CDATA. General rule going forward: anything DOM-fidelity-sensitive needs a real parser (happy-dom `Window`/`Browser`) in its test, not markup-string inspection.

- [x] dependency extraction was conflating two separate steps (found via review, fixed 2026-08-13): (1) NAME RESOLUTION -- does `foo` in `this.foo.bar` refer to a reachable named (`:aka`) scope at all, and (2) DEPENDENCY RECORDING -- given (1) says yes, note `{ via: 'foo', key: 'bar' }`. Step (2) is mechanical once (1) is answered correctly; the actual bug was that step (1) was answered via a flat, page-wide `page.defines` map (`stage1-load.ts` had its own `//TODO: this is probably wrong` next to it) instead of walking the IR scope tree -- meaning two unrelated `:aka="foo"` scopes in different branches would collide, and reachability from the reference's actual position was never checked. Fixed: `page.defines` removed entirely; `stage4-resolve.ts`'s `findNavigableScope(scope, name)` now walks up `scope.parent` (mirroring the runtime's own `CoreScope.lookup()`), checking at each ancestor whether IT has a named child scope called `name` (found -> navigable) or an ordinary value of that name first (found -> shadowed, not navigable, matching real lookup precedence). Ascending PAST an intermediate ancestor to find where a single named reference is declared now works correctly (added a test for it), as does shadowing (added a test for that too).

- [x] chained scope navigation in dependency extraction -- fixed 2026-08-12. `matchDep`'s two hardcoded shapes (`this.key`, `this.<via>.key`) are gone; `stage4-resolve.ts` now consumes a `this`-rooted chain WHOLE (`chainSegments`) and walks it one segment at a time (`resolveChain`), resolving each against the scope the previous segment landed in -- mirroring `CoreScope.lookup()`. `ValueDepRef.via` became `string[]`, and `stage7-generate.ts`'s `makeDep` emits the corresponding `this.a.b.$value("key")`.
  - The severity here was worse than "unrecognized": the old code didn't fail to match, it matched a PREFIX and then `this.skip()`ped the rest. `outer.inner.count` recorded a dep on `outer.inner` (a scope object, never changes) and `$parent.$parent.n` recorded one on `$parent.$parent` (a parent pointer, fixed for the scope's life). Both compiled with ZERO errors and produced a binding that silently never updated -- the worst failure shape for a reactive language, and invisible to any test that only checks first render.
  - Found while fixing it, same failure class, different stage: `stage3-qualify.ts`'s `isQualified` treated the property of a COMPUTED member as already-resolved, so the `i` in `${items[i]}` was never qualified -- it became an undeclared global (swallowed ReferenceError) contributing no dependency at all. One-line fix (`!parent.computed`); `${items[i]}` is common enough that this mattered more in practice than the chain case.
  - "Unrecognized" is no longer allowed to be a quiet no-op anywhere in stage4: a navigation segment that doesn't resolve is a compile error, and a computed access on a named scope (`outer[k]`, statically unfollowable) is now reported rather than silently recording a dep on the scope itself.
  - Regression coverage is at the runtime level on purpose (`test/runtime/web/scope-chains.test.ts`): it compiles real source, runs the generated props through `WebContext`, mutates a value and asserts the DOM text CHANGED. All 4 fail against the pre-fix compiler with stale text; a compiler-only assertion on `deps` would have been much easier to fool.
