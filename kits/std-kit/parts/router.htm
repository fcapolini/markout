<:define tag="std-router:div" /* The names the routes answer to. Discovered, not declared: a route CALLS `add`, so the write happens in the router's own scope and the route never reads the registry -- which is what keeps it from re-running itself. Assigning `$host._names` from a route would, and pushing into it would notify nobody. This needs a render that settles. A scope's own values are evaluated before its children exist, so every name arrives after `page` below has already been computed once; `page` is marked dirty by the write and the refresh walks again to carry it. See CoreContext.refresh() -- before that, this shape rendered two routes at once on first paint and only agreed with itself after a navigation. Nothing here reads whether a PEER matched, which is the rule that keeps ranking from being mutually recursive -- see docs/design/advanced-router-kit.md. */ :_names=${[]} ::add=${(n) => { _names.includes(n) || (_names = [..._names, n]); }} /* The two ways an address can fail to name a page, which are different questions and want different answers. `defaultPage` is what to show when the address names NO page: a bare `/`, and a page rendered with no address at all -- `markout build` without an `--origin`, where `$url` is undefined. Both mean nobody said which page, and the answer is the site's front door. `fallback` is what to show when the address names a page that does not exist -- `?abuot`, or `?utm_source=nl` where the query was never a route name at all. That is the 404 question, and a site that wants a visible one points this at a route of its own. Kept apart because folding them together puts the wrong page at the front door: with one parameter, `::fallback="notfound"` would answer a bare `/` with the 404. `fallback` follows `defaultPage` unless it is given one of its own, which is the answer a site without a 404 screen wants and the one it would otherwise have to say twice. Defaulting it to the literal `index` instead was a trap the router demo walked into on its first run: a page whose front door is `overview` set `defaultPage` alone, and an address naming nothing real -- `?utm_source=nl` -- resolved to an `index` route that did not exist and rendered a blank frame. */ ::defaultPage="index" ::fallback=${defaultPage} /* How many routers this one is inside, and so which segment of the path it owns. Each asks the nearest router above it and adds one, so no router knows its ancestry beyond that one step -- and `$outer` is a walk, which is what lets it see past the `` in between. */ ::depth=${($outer('std-router')?.depth ?? -1) + 1} /* The query up to its first separator, split on `/` so one address can name a page at every level: `?about` names a page, `?about&x=1` names the same one, and `?about/team` names `about` out here and `team` to a router nested inside it. A level the address says nothing about falls to `defaultPage`, which is what `?about` gives a router below it. Guarded because a page can be rendered with no address at all, and `$url` is undefined there. Unguarded this threw twice and took the whole render with it, which would rule out the one deployment this part is most for: a statically built page, served as files, routed entirely in the browser. */ :_search=${($url?.search ?? '').replace(/^\?/, '')} :_path=${_search.replace(/[&;=].*$/, '')} :_asked=${_path.split('/')[depth] || defaultPage} /* An address naming no route resolves to the fallback, and it resolves there while RENDERING -- so the served markup already shows the right page and a browser with no Navigation API needs nothing further. */ ::page=${_names.includes(_asked) ? _asked : fallback} :_handler=${null} /* Browser-only, and absent where the Navigation API is: `navigation` is read off `globalThis` with `?.`, so a browser without it simply never registers and every link stays an ordinary link. That IS the multi-page mode -- there is no second code path for it. */ :did-init=${() => { _handler = (ev) => { /* Let the browser handle anything we can't or shouldn't take over. `reload` is the one that is easy to miss and the most annoying to get wrong: a reload fires `navigate` like anything else and CAN be intercepted, and intercepting it means the document is never refetched -- so the user presses reload and watches the page re-render the bytes it already had. */ if ( !ev.canIntercept || ev.hashChange || ev.downloadRequest !== null || ev.formData || ev.navigationType === 'reload' ) { return; } /* A different document is a different document. `canIntercept` is true for any same-origin navigation, including one to another PAGE -- and intercepting that cancels the load of a document this router knows nothing about. The address bar moves, no route here answers to it, and the page sits there until someone reloads by hand. The pathname is where a round trip is meant to happen, which is the whole division this part rests on: the pathname decides where one is unavoidable, the query decides everything inside one. So only a navigation staying in this document is ours to cancel. */ const to = new URL(ev.destination.url); if (!$url || to.origin !== $url.origin || to.pathname !== $url.pathname) { return; } /* No handler, because there is no work to do. intercept() is what cancels the real navigation: the URL and the history entry update and no document load happens, then `navigatesuccess` fires and the runtime moves `$url` -- which is what `page` above is reading. */ ev.intercept(); }; globalThis?.navigation?.addEventListener("navigate", _handler); }} :will-dispose=${() => { globalThis?.navigation?.removeEventListener("navigate", _handler); }} > <:slot/> <:define tag="std-route:div" ::page="index" /* Says this route's name, so the router knows it exists whether or not it is the one showing. It reads the route's OWN `page`, never the router's, so registering cannot re-trigger registering. */ :_reg=${$host.add(page)} :_routerPage=${$host.page} // public because a page wants it: `${home.selected}` on a nav link ::selected=${_routerPage === page}>
